- Payment aggregator choice: PayMongo (PH-first, simpler, cleaner docs) vs. Xendit (broader SEA reach, more setup complexity) for the Billing & Subscription API's GCash/bank-transfer support.
- Wikidata vendor seeding: V2's SPARQL query only returned ~2,600 entries and missed real PH SMBs (e.g. "Chooks To Go") — likely an overly narrow query filter, worth a real investigation pass to loosen it, not a data availability problem.
- Line-item extraction: V2 never got this reliably working even when OCR clearly showed the items — flagged as a genuinely harder sub-problem needing real design attention in a later session, not resolved yet.
- Historical Excel snapshot preservation — concrete scenario: a user downloads an Excel export, hand-signs or annotates it (e.g. an auditor's requested note in the margin), and submits *that physical file* to a BIR auditor. That submitted file is never reimported (annotations aren't data changes, there's nothing to write back), so the system never sees it again after download. Later, if there's ever a dispute needing proof of exactly what was submitted on that date: the system can always regenerate an export matching that date's underlying data via Historian's event log — but that regenerated file won't carry the hand-written annotations/signature, since those never existed as system data. If the literal submitted artifact (with annotations) ever needs to be retrievable, that requires a new capability that doesn't exist today — an explicit "archive this exact file before I send it externally" action, storing the literal bytes as evidence, distinct from both Historian (tracks data changes, not external-facing snapshots) and Archive Sync (mirrors processed receipts, not generated exports). Still open: does this ever actually matter for compliance, or is data-level regeneration always sufficient?

## Decisions Log

- **IPC / process architecture**: gRPC (HTTP/2-based) as the transport between control panel, execution core, and inference server(s). OS-agnostic, typed `.proto` contracts double as API documentation, and server-streaming solves V2's "results only show at end of run" bug via live progress streaming to the control panel.
- **Background Workers**: non-LLM workers run in-process within the core (thread/process pool) behind the Background Workers API contract — no separate worker-server process. LLM-driven background work is not a separate subsystem; it's a batch inference job (prompt + tool calls) dispatched through the Inference API.
- **Interface transport is decoupled from interface look-and-feel**: gRPC does not imply a web app. Control panel can be a gRPC client regardless of whether it's a TUI, native desktop app, or web app.
- **Two frontends**: Textual TUI = admin/status console for the always-on server (config, health, run monitoring). Separate web app = end-user surface (upload, view/manage own receipts), reachable via Cloudflare Tunnel.
- **Gateway over gRPC-Web**: a thin REST + WebSocket gateway (FastAPI) sits in front of the gRPC core translating browser calls; all real logic stays in the gRPC core so self-hosted single-user installs can skip running the gateway entirely.
- **Single core, dual deployment mode**: a `tenancy_mode` config flag — `single` (self-hosted, one implicit user, no login) vs `multi` (accounts/sessions active) — same code path either way. Supports both "sell the program for private self-hosting" and "run our own paid multi-tenant service" without a codebase fork.
- **Save API confirmed**: one folder per user = one local git repo per user. Isolation is structural (folder/repo boundary), not just a permissions check.
- **Auth**: SSO (OAuth2/OIDC, e.g. Google) handles authentication only. After SSO succeeds, issue a server-side session + httpOnly secure cookie for the actual web app session (not the IdP token, not a JWT to the browser) — chosen over JWT specifically because owner/staff remote-control access needs instant revocation, which stateless JWTs can't give without a blocklist. A separate short-lived signed-token mechanism is reserved for future machine-to-machine/API access, not human sessions.
- **Role tiers**: `owner` / `staff` / `client`. Owner and staff can remote-control the internal server (start/stop runs, config, view queues); enforced at the gateway layer by role claim before requests reach the gRPC core. Client role is confined to their own folder/repo via the Save API's folder-isolation contract.
- **Concurrent multi-user runs**: confirmed as core design (not sequential like V2). Execution Core needs a run scheduler supporting multiple simultaneous run contexts, each scoped to its user's folder/repo. Two distinct concurrency knobs: per-user concurrency limit (default 1, doubles as rate limiting) and a separate global concurrency cap protecting shared OCR/inference resources. Every OCR/Preprocessing/Inference API call takes a `run_id`/`user_id` context — no shared mutable state assumed.
- **Staff access to client data ("break-glass")**: not standing access. Staff must request an explicit, reason-tagged (support ticket/debug note), time-boxed access grant to a specific client's folder — a distinct mechanism from the staff role itself, not a permission bit. Every grant is logged.
- **Staff vs. owner server control split**: staff = operational (view run queues/health, restart stuck/failed runs, view logs). Owner-only = global config changes, user/role management, stopping the server, billing/tenancy settings.
- **Notifications**: both the owner and the affected client are notified via the in-app inbox system when a break-glass access grant occurs (not just an audit log).
- **Per-run performance tiers**: monetization lever built on top of existing tunable knobs — number of OCR engines run in corroboration, number of preprocessing presets generated/tested, which inference hardware/model tier is assigned, and scheduler priority/concurrency allowance. Tiers are named config profiles (`basic`/`pro`/`enterprise`) — data bundles of the same underlying knobs, not special-cased logic per tier. **Which ingestion sources a tier can submit through is a recognized future knob in this same bundle** (Ingestion API's own deep-dive, `v3-deepdive-04-ingestion-api.md` §1 — e.g. the scanner or Drive reserved for higher tiers) — not built yet, sequenced behind Architect's tier-profile-definition registry and Billing/Execution Core's tier-application mechanism actually existing, but Ingestion's `SourceRegistry` is already shaped (`user_id`/`run_id`-context-aware lookup) to absorb it as a resolution-source swap rather than a redesign once that mechanism lands.
- **Config storage**: each user's config lives as a file inside their own folder/repo (consistent with folder-per-user Save API isolation); tier changes update that file. Background workers and Reconciliation/vendor-learning always run against the stored config in the user's folder, not "whatever tier they're on right now" at trigger time — keeps historical runs reproducible/explainable.
- **Vendor learning scope (Matching/Reconciliation API)**: two independent per-user config toggles rather than one combined mode — `contribute_to_global` (opt-in consent, whether this user's learned vendor corrections merge into a shared global vendor knowledge base) and `read_scope` (`local_only` vs `local_and_global`, whether matching consults only the user's own learned data or also the shared set). Conflict resolution: local always overrides global for that user's own matching. Contribution pipeline must scrub any link back to the contributing user/account before merging into the global set (the vendor data itself is fine to share; the "who submitted it" metadata is not) — a structural requirement on the Learning API pipeline, not a later policy patch.
- **Vendor/Branch data model**: Vendor (canonical brand-level entity: name, vendor-level TIN if any) and Branch (belongs to a Vendor: address, franchiser name, franchiser TIN — lives at branch level since branches of the same brand can have different franchisers/TINs). Matching resolves OCR'd address/TIN to a Branch first, which resolves up to its parent Vendor.
- **Logs API storage**: day-rotated (wall-clock day, not per-runtime — a restart mid-day continues appending to that day's existing file rather than creating a new one), split across two independent axes: scope (per-user vs. global) and time (one file per day per scope), e.g. `logs/user/<user_id>/2026-07-14.jsonl` and `logs/global/2026-07-14.jsonl`. Rotation boundary (UTC vs. local time) and retention/archival policy left as open questions. Logs are gitignored — NOT committed via the Save API's git mechanism, since git history is append-only (deleting a file later doesn't remove it from history) and verbose logs containing real receipt content shouldn't live forever in git; read-access still follows the same per-user permission rules as Save API, but storage/retention is handled separately by the Logs API itself.
- **Billing & Subscription API / PSP choice**: leaning PayMongo over Xendit for the initial build — transparent public pricing, PH-first simplicity, faster solo-dev integration; Xendit held as the likely switch if the wholesale/self-hosting side goes genuinely regional (broader SEA coverage, built-in recurring billing/disbursement). Both are tokenizing aggregators (card/GCash credentials never touch the system directly, no PCI scope taken on). Architectural requirement regardless of choice: PSP credentials must be per-install config (like every other tenancy-aware setting), not hardcoded to one merchant account — otherwise self-hosted buyers would route payments through the reference deployment's own account. Billing API should be built against a small internal payment-provider interface (verify webhook, create charge, check status) so the PSP is swappable.
- **Self-hosted Nominatim: local vs. VPS hosting, resolved as a phase split, not a permanent choice.** Runtime RAM footprint for a PH-only extract is ~1-2GB hard-allocated (small `shared_buffers` + per-connection `work_mem`, tuned down from planet-scale defaults) — genuinely cheap, not competing meaningfully with a constrained dev box. For dev/testing now: run locally (NUC or similar) — zero network dependency, fastest iteration. For the actual 24/7 production service: lean toward a VPS (or the dual-Xeon server, conditionally on it having genuine server-grade hosting — UPS, wired connection) rather than home hardware — the deciding factor is reliability class (datacenter uptime vs. residential internet/power), not resource contention. This is a config-selectable target (local Docker container vs. remote URL) behind the same Provider Registry interface, not a one-time irreversible decision.
- **Inference API — multithreaded-run stalling, root cause identified from V2 and fixed in design.** Confirmed via V2's actual code: `_compute_receipt` already runs each receipt independently in a thread pool (OCR/vision/matching genuinely proceed per-file, not stalled by siblings) — the real bottleneck is `llm_fixer.LLM_CALL_LOCK`, a hard constraint (a single loaded ONNX/llama.cpp model has non-reentrant generator state, cannot serve two `generate()` calls at once). Every receipt needing an LLM step queues on that one lock, and since the LLM step is usually the dominant per-receipt cost, it becomes the real bottleneck regardless of OCR thread count (Amdahl's Law). **No-GIL does not fix this** — the GIL was never the bottleneck, a shared native resource that can only do one thing at a time is. **The actual fix, confirmed as the target design**: since Inference already runs as its own separate process/server (not an in-process lock shared with the TUI/everything else), a receipt waiting on its LLM step should `await` that gRPC call asynchronously rather than block an OS thread doing nothing — freeing the caller to keep other receipts' OCR/preprocessing/matching moving while the wait is pending, which directly eliminates "one receipt stalls the others just because something is waiting." Complementary, not required for this specific fix: true batched inference (multiple prompts in one forward pass, directly answering the original "should be BATCH not single" complaint) and optional multiple model instances across available hardware — both increase throughput, but the async non-blocking wait is what eliminates the stall itself.
- **Full V2 gap-check session (file reads + full 256-commit history scan) — findings folded into the relevant Core API entries above:** Health API gained a Watchdog sub-API (liveness-kick/auto-restart, distinct from crash detection, tracks per-instance version/commit for A/B hot-swap, version info rides the heartbeat response only — not every business response, to keep the hot path clean). Matching API gained a formal Vendor Directory sub-package (alias lists, Wikidata-seeded global bootstrap with realistic scope limits — name/category only, not TIN/franchise data — global contribution audit using a git-tracked collaborative-review layer alongside the queryable SQLite store, category-classification as a named capability spanning Matching+Inference, and a two-way fuzzy match: forward candidate-to-DB plus a reverse gazetteer scan of known names against the full raw OCR text, cost-scoped to a plausible subset). Background Workers API gained an explicit idle-time execution class and was clarified as the generic execution substrate that domain APIs (including Reconciliation) run on top of, not a competing owner of business logic. Persistence API gained an extensible typed-reference-identifier concept for receipts (license plate, account/policy numbers, etc. — never a fixed column per type) and adopted V2's live-formula Excel summary-sheet technique plus a file-open-tolerance requirement for exports. Logs API gained explicit full-traceback-always and verbosity-tier requirements. Inference API gained three concrete hardening requirements: real locking on lazy model loading (not just the generation lock), shared weights for multimodal presets (no RAM/VRAM doubling), and graceful truncated-JSON handling. Update API gained a stale-bytecode-clearing requirement for the release-dir swap, plus multithreaded/async model and dependency downloads (including HF token-auth support for gated models). Review/Flagging API gained a concrete flag taxonomy sourced directly from V2's real reconciliation checks (VAT math, malformed TIN, implausible dates, orphaned/missing archive references, account outliers, duplicate rows, mislabeled vendor groups, items-vendor mismatches, reimport conflicts) instead of a vague generic bucket. Reconciliation & Learning API's 2-page Excel question resolved (live-formula summary page) but the API itself is explicitly flagged as needing a real design pass in a later session. Line-item extraction flagged as a genuinely unsolved hard problem (V2 never got it reliably working) requiring dedicated future design attention, not solved today.
- **Setup API — Google Drive config-restore flow**: on fresh instance setup, after owner SSO, the Setup API checks whether that Google account was used to set up a previous instance and offers to restore config/credentials (HF token, other API keys, other hard-to-reconfigure settings) from a config bundle backed up to that account's Drive. The bundle must be encrypted before it ever leaves the machine, with a passphrase set during original setup and re-entered to decrypt on the new instance — Drive is transport only, not the security boundary (OAuth access to the Drive account is access control, not encryption; a compromised Drive account shouldn't mean plaintext secrets are exposed). Reuses the swappable backup-storage interface pattern, with mandatory encryption layered on top given the sensitivity of the contents.
- **Blob hash algorithm confirmed as SHA-256** — not MD5 (broken, real collision attacks exist), not SHA-512 (unnecessarily large for no real benefit at this scale); SHA-256 is the modern standard for content-addressable storage (same direction Git itself is migrating, same default used by IPFS's multihash).
- **Windows Explorer metadata tagging for blobs — considered, then explicitly reversed.** The idea (writing vendor/amount/category into standard Explorer-recognized fields like Title/Tags/Comments via embedded EXIF/XMP so files are sortable in Explorer without a custom shell extension) was scoped and a fix designed (immutable hash-addressed original + separate regenerable "browsable copy" carrying the tags, avoiding the hash-changes-when-tagged problem) — but ultimately rejected in favor of keeping blobs purely immutable with zero embedded metadata. Browsing/sorting/filtering is handled entirely by the webapp via the Search/Query API's structured SQLite data instead of filesystem-level tricks — simpler, and not limited to single-user/self-hosted mode the way an Explorer-only solution would have been.
- **Top-level directory architecture, final resolved form — supersedes both earlier fixed-two-slot and generic timestamped-release-dir versions:** Distribution is a per-OS GitHub Release ZIP containing only the setup script (not a source snapshot or git archive). Running it performs the first `git clone`, then hands off to the Setup API code inside that clone. Setup API builds the top-level directory — config, default data folder paths, the `start.bat`/`start.sh` launcher, models and any other downloadable assets — entirely **outside** every release clone, as siblings not children, so user data (and large slow-changing assets like models, which aren't duplicated per-release and are referenced by path from whichever release is active) is architecturally unreachable by any update/clone-replace operation.
  - **Release directories are named, multi-channel, and garbage-collected — not a fixed slot count.** Each release clone is named `<version>_<short-commit-hash>` (reusing the existing versioning scheme directly — every commit already has a distinct `pp` segment, so even the Latest-Commit channel needs no special-casing). Users choose a channel: LTSC / Stable / Beta / Alpha are user-selectable (extends the existing `update_channel` config from binary to these four); **Latest-Commit is owner-role-only**, fitting directly into the existing owner/staff/client permission model. A Background Worker (idle-time execution class) periodically garbage-collects release directories that are (a) not currently active, (b) unused past a configurable retention window, and (c) outside a minimum-keep floor — always retain the current release plus at least one immediately-previous one regardless of age, so one-step-back auto-rollback never depends on GC timing.
  - **Runtime Manager / Supervisor lives outside every release clone, at the top level — this is a bootstrapping requirement, not a preference.** If the component deciding which release is active and launching each service's processes were itself part of a release's code, there's a self-referential problem: which release's copy is in charge during a rollback of that very release? The Supervisor is a small, deliberately stable top-level component: reads the active-release marker, launches each configured service as a subprocess pointed at that release's own code and venv, runs health checks via the Health API, flips the marker on successful cutover, drives rollback. It has its own separate, more conservative update path than regular app updates, since it's load-bearing for the whole update mechanism.
  - **Venvs are per-service, per-release** (`<release>/services/ocr/.venv/`, `<release>/services/inference/.venv/`, etc.), not one monolithic venv per release — the direct extension of already running OCR/Preprocessing/Inference as separate processes for crash isolation to also isolating their dependency environments (prevents real conflicts, e.g. OpenCV's vs. ONNX Runtime's numpy pin). Each service subpackage carries its own dependency manifest committed alongside its code, so every release clone has exactly the right pinned versions per service. The Supervisor launches each service using that service's own venv interpreter path within the currently active release — answers both "how do different APIs get different venvs" and "which commit's code is actually running" with one mechanism.
  - **Tooling: `uv`, confirmed**, replacing pip+venv+requirements.txt — fast, cheap per-project venvs backed by one shared package cache, which is what makes the many-small-venvs-per-service pattern practical rather than a management burden.
  - Health-gated cutover, drain-before-eligible-for-reuse, and the manual-`update.bat`-must-use-the-same-mechanism rule (not a separate `git pull` path) all carry over unchanged from the earlier design. A self-referential setup/update script must never try to move or delete itself mid-run (fragile, especially on Windows with locked executing files) — hands off remaining file operations to Setup/Update API's own Python-level finalize routine instead.
- **Runtime Manager/Supervisor deployment model, fully resolved**: same repo as everything else (no second repo — avoids a second CI pipeline/versioning scheme for a genuinely small component), living as its own subpackage (`runtime_manager/`) alongside the `services/<api>/` packages, subject to the same hygiene rules. What differs is deployment: Setup API *copies* (not symlinks, not "points at whichever release is active") the Supervisor's code + its own small venv out into the top-level directory as `_supervisor/`, decoupled from any single release's lifecycle from that point on. Updating it is explicitly **not** part of the regular automatic channel-based update flow — the Update API surfaces a separate, explicit "Runtime Manager update available" prompt requiring real owner confirmation, with an extended smoke-test pass before the swap (higher bar than regular releases, since a bad Supervisor update has nothing left to roll it back automatically). This reuses per-API versioning for a genuinely useful purpose: comparing "installed Supervisor version" (in `_supervisor/`) against "the Supervisor version sitting inside the currently active release clone" is a normal version comparison, not a special mechanism.
- **Execution Core API formalized (#25) — the actual "running loop," found to have never been named despite being one of the most important APIs (mirrors V2's own core gap: `daemon_loop`/`run_once` were never a formal, bounded component either).** Full design, grounded in reading V2's `processor.py`/`main.py` in full:
  - **Content-hash-based idempotency (SHA-256, size+hash pair), not filename/mtime** — directly validated by V2's own `_file_fingerprint()`, which is deliberately NOT mtime-based because cloud sync (Drive/OneDrive/Dropbox) touches mtime on unchanged bytes, which would cause false reprocessing. Blob-level dedup (same hash = same blob) and run-level idempotency (has this content been fully processed into a DB row) are tracked as two distinct concerns, not conflated.
  - **Per-stage checkpointing for resumable retries — the one genuinely novel technique adopted this session.** V2 retries a whole receipt from scratch on any failure, wasting already-completed expensive steps (especially LLM inference) on retry. Fix: same principle behind durable workflow-execution systems (Temporal, Prefect, Dagster) — adopted as the *technique*, not the framework, consistent with the earlier Tool Call orchestrator decision to build custom rather than adopt LangChain (avoids real operational overhead like Temporal's own server infrastructure for what's a bounded, modest problem here). Execution Core writes a small stage-checkpoint record to Persistence after each pipeline stage completes (ingested → preprocessed → OCR'd → matched → geo'd → inferred → written); a retry after crash/failure resumes from the last completed stage instead of redoing everything.
  - **Bounded retry with escalation, not infinite retry** — V2's `.failed_attempts.json` sidecar + quarantine-after-max-attempts (real motivating bug: "one bad scan produced 57 identical warnings in a single session") becomes, in V3, escalation to a new Review/Flagging flag type ("processing failed repeatedly") after N failed attempts, rather than a physical `failed/` folder move which doesn't fit the folderless blob model.
  - **Fine-grained, responsive cancellation** — V2's real bug ("a 156-receipt extreme-mode run used to keep going for many minutes after 'q'") is fixed by checking the stop/cancellation signal per-receipt within a run, not just between runs.
  - **Explicit state machine** (paused/running/waiting-for-trigger/shutting-down) rather than scattered threading-Event flags, matching this plan's general preference for explicit over implicit state.
  - **Hybrid push/poll ingestion triggering, not pure polling like V2's fixed `poll_interval_seconds`.** Direct web upload and the in-browser scanner trigger a run immediately (no polling needed at all). Google Drive uses real push notifications (webhook via Gateway + the existing Cloudflare Tunnel) as the primary trigger — verified current and usable — with two real caveats accounted for: Google gives an expiration timestamp but no warning before it lapses, and current developer reports describe webhook channels occasionally dying silently before their stated expiry. Mitigated by Ingestion API's Webhook Subscription Manager sub-API (generic, provider-agnostic — same mechanism would handle other push-capable sources later), whose Background Worker (idle-time class) proactively renews the channel ahead of its known expiration, plus a much-less-frequent, configurable fallback poll (daily is fine, not just hourly — its only job is catching a rare silent-failure case, not being a primary mechanism) as a safety net — push-first, poll-as-safety-net, not either alone.
  - **Fine-grained Watchdog integration** — kicks the Health API's Watchdog at multiple points within the loop (start of each cycle and throughout any idle wait), matching V2's proven wiring, so a genuinely hung run is caught, not just a hung idle loop.
  - **Config hot-reload every cycle** — config changes apply to the next run without requiring a full service restart, tracked via a reload counter for observability.
  - **Clean separation from Interface is now structurally guaranteed, not just a design goal** — V2's `daemon_loop` literally instantiates the menu system, keyboard listener, and dashboard inside the same loop that runs the pipeline; V3's process separation makes that specific coupling architecturally impossible to reintroduce, since Interface only ever reaches Execution Core through its gRPC contract.
  - **Debounce-with-max-wait coalescing before a run starts, and an explicit open/closing run lifecycle enabling mid-run intake.** A single push notification firing an immediate one-file run would defeat the whole batch-first design. Standard debounce pattern: the first trigger starts a short, configurable coalescing window; each additional trigger arriving within it resets/extends the window, so a burst of near-simultaneous uploads collapses into one run; a hard max-wait ceiling forces the run to actually start even under a continuous trickle of arrivals, so it never waits forever. This lives in Execution Core's scheduler (not the Webhook Subscription Manager, which only ever emits "new file available" events — Execution Core decides how to batch them). Runs have two explicit phases: **open** (still accepting new file intake — a late-arriving file just joins the current run's task queue if there's capacity) and **closing** (finalizing the batch's Persistence writes, including its Historian sub-package's event log, and triggering the completion notification — no new intake; Excel is never generated as part of a run, it's an on-demand export from the webapp entirely separate from run lifecycle). Transition to closing happens when the debounce window elapses with in-flight work sufficiently progressed, or a max-run-duration/file-count cap is hit (same debounce-with-ceiling principle applied at the run level). Real payoff: a straggler file arriving mid-run joins the currently open run instead of needing to wait for a whole new run slot under the per-user concurrency limit — better batching, less waiting, not just a nicety.
- **CORRECTION — Historian API retired as a standalone API; folded into Persistence as a sub-package.** Caught via a direct challenge to re-derive the mechanism from scratch rather than defend what was already written. The original design (a separate git-committed event log, distinct from the SQLite database) never actually earned its complexity once traced through properly: the live `.sqlite` file was already never going to be git-tracked directly (decided earlier, for WAL/binary-safety reasons) — so "Historian" was only ever writing a *parallel* structured text record to git, not versioning the real data. "Rollback via git" wasn't actually free either: since the SQLite data itself stays outside git, a `git revert` could only hand back an old *event record*, which the application would still have to replay as a new write to undo anything — the same work a plain SQL table would need, with none of git's benefit. And the real consumer of "show this receipt's history" is the webapp querying through an API, not a human running `git log` — building that query layer over git history is strictly more work than a normal `SELECT` over an events table. **Fix**: Historian becomes `persistence/historian/`, an append-only `events` table living in the *same* database as the data it describes, so a data write and its audit event commit atomically in one SQL transaction — something two separate services could never guarantee. Same fields as before (table/row/before-after/actor/version/timestamp), same query pattern (filter by receipt ID = edit history), same Reimport merge-base role (now an event sequence number instead of a commit hash) — nothing about what it *does* changed, only how it's stored. GitHub remains available as a legitimate optional export/mirror of the events table (the original, narrower idea before this scope-crept into a whole API) for anyone who wants `git log`-style browsing or free off-site durability — a feature, not core infrastructure.
- **CORRECTION — Architect's `temporal_learning` submodule likewise dropped git in favor of a plain moderation-queue table.** Same root problem, same fix: the global vendor contribution review flow (propose → LLM-prescreen → staff-review → approve/merge) is a standard moderation-queue pattern — a `contributions` table with a status column (pending/approved/rejected), old/new value columns, a reviewer field — that a webapp renders directly from columns, which actually serves the review UI *better* than parsing a git diff would. Git added a second storage system to keep consistent with the primary registry for no corresponding benefit, same as the Historian mistake.
- **Structural note on why this became a sub-package of Persistence rather than staying a peer API (or fully merging into one undifferentiated blob)**: transactional consistency is the deciding factor, not just "fewer APIs is simpler." Keeping Historian as a clearly-named sub-package (not dissolving the distinction entirely) preserves the internal separation of concern between "current state" tables and "what changed" tables, while the shared database/transaction boundary is what makes atomic dual-writes possible. **API count note, kept current rather than frozen at the point of this correction**: this correction dropped the count from 26 to 25 at the time it was made. Since then, three genuinely new top-level APIs were added (Content Security #26, Telemetrees #27, Account Guardian #28) and one new sub-API was added under Persistence (Disaster Recovery, `persistence/disaster_recovery/`) — current total: **28 core APIs**, see file 01 for the authoritative numbered list.
- **CORRECTION — "Excel bidirectional editing" removed from the Open Questions Log; it was stale, already answered in a prior session and mistakenly left listed as open.** Yes, hand-edited exports are expected to flow back in — this is exactly why the Reimport sub-API (`persistence/reimport/`) exists in file 01's Persistence entry, and it stays there rather than moving to Ingestion despite conceptually being "receiving a file from outside the system": its actual job (diff against canonical state, resolve conflicts, apply through the normal write path) is a Persistence-write concern, not an acquisition/normalization one. The round-trip is an explicit, user-initiated action, never a live sync: export generates a file server-side, the user downloads their own copy, edits it locally, and explicitly re-uploads through Reimport — there is no file the server and the user's local Excel are ever both touching at once. This also means **V2's file-open-tolerance requirement (writes must tolerate the workbook being open in Excel) is now fully obsolete**, not just less relevant — V2's collision was a same-machine, live-file problem that V3's client/server split architecturally eliminates rather than needing to handle more gracefully. File 01's Persistence entry updated accordingly.
