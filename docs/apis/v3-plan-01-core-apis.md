# V3 Plan (2/5: CORE APIs)

**Companion files:** `v3-plan-00-index.md` (postmortem/audit instructions) · `v3-plan-02-architecture.md` · `v3-plan-03-decisions.md` · `v3-plan-04-v2-audit-findings.md`

## Core APIs (v0.1 skeleton — scope to be refined per-session)

**All 32 APIs below now have their own full deep-dive document** (`v3-deepdive-01-ocr-api.md` through `v3-deepdive-28-telemetrees-api.md` for the original 28; #29-32 have their own numbered deep-dives cited in their entries below) — package layout, data contracts, dependencies, hardware/concurrency, gRPC surface, config, testing hooks, and open questions for each. This file's own entries are the original skeleton-level summary and remain useful as an index and for cross-cutting rules/naming, but where an entry below and its own deep-dive document differ in detail, **the deep-dive document is authoritative** — this file gets updated opportunistically when a correction is significant enough to affect the summary itself (as several entries below already reflect), not on every detail the deep-dive adds.

1. **OCR API** — multi-engine, parallel execution across engines per file, corroboration/voting layer. **Full design in this API's own deep-dive** (`v3-deepdive-01-ocr-api.md`): engine roster (Tesseract, RapidOCR, PaddleOCR, Windows OCR, Apple Vision, plus a Google/Azure/AWS cloud tier), tiered deterministic-then-escalate corroboration, hardware EP selection, and the asyncio/free-threading/profiling checklist.
2. **Preprocessing API** — generates and tests multiple presets (color channels, grayscale, B/W, contrast variants) via a process pool (not threads — OpenCV's free-threaded wheels aren't ready, tracked upstream at `opencv/opencv#27933`); feeds variants into OCR API; **hardware acceleration path resolved in this API's own deep-dive** (`v3-deepdive-03-preprocessing-api.md`): OpenCV's Transparent API (UMat/OpenCL) is the default GPU path (vendor-agnostic, ships in the standard wheel); GNA and IPU are both dead ends for this API specifically (GNA never supported 2D convolution and is being discontinued; Intel's own IPU is a camera-capture-time image-signal-processor with no live sensor in this pipeline to sit between — a different, real piece of hardware from Graphcore's unrelated IPU); "transcoding engine" resolved as Intel Media SDK/oneVPL (Intel VPL) — real, checked, deliberately not adopted for this API given its lack of Python bindings, single-vendor lock-in, and video-frame-rate-oriented design, kept as a named bulk-reprocessing escape hatch rather than a v1 dependency.
3. **Inference (LLM) API** — ONNX-based, defined role as parser/corroborator (not a competitor to scoring logic); multi-backend (CPU/MLAS, CUDA, TensorRT, OpenVINO, Windows ML, QNN, MIGraphX for AMD — MIGraphX is the current AMD path, the ROCm execution provider itself was removed from ONNX Runtime as of the 1.23 release); multi-hardware agent splitting (different models on different devices by task); batch-first. **Full design in this API's own deep-dive** (`v3-deepdive-02-inference-api.md`): single-backend decision (`onnxruntime-genai` only, no llama.cpp carried forward), native constrained decoding via LLGuidance replacing V2's prompt-engineering/salvage-parsing approach, the `PresetWorker`/lazy-load-locking concurrency mechanism, and the proposed Setup-API-as-shared-hardware-substrate resolution (shared with OCR API's own deep-dive). Callers `await` inference requests asynchronously rather than blocking a thread on a shared lock — a receipt waiting on its LLM step never stalls other receipts' concurrent work (see Decisions Log: root-caused from V2's `LLM_CALL_LOCK` stalling behavior). Lazy model loading needs real locking (not just the generation-call lock) to avoid a load race; multimodal presets must share weights rather than double-loading (RAM/VRAM doubling); structured-output (JSON) parsing must handle truncation from token-budget cutoffs gracefully — detect and retry with more budget, or salvage partial output, never hard-fail. **Vision/multimodal as a planned, native ONNX Runtime GenAI capability**, not a bolt-on — a vision-language model reading the receipt image directly as a corroboration source independent of OCR text (onnxruntime-genai has real multimodal pipeline support, e.g. Qwen2-VL/Phi-4-multimodal-style presets). Never actually confirmed working in V2 on either backend it tried (llama.cpp's multimodal support was unreliable enough to help motivate the ONNX move; by the time V2 was on ONNX, baseline functionality took priority and vision was never verified end-to-end) — genuinely a from-scratch feature for V3, not a port. **The sole exception to multi-channel concurrent instances (see Update API)**: Inference never multiplies per channel. Loading a full model copy per active channel would be prohibitively wasteful of RAM/VRAM — the same concern as the existing no-double-loading-weights rule for multimodal presets, just at fleet scale instead of per-process. Regardless of which channel a user's other services are running on, their inference requests route to one shared Inference API instance, pinned to the system's primary/Stable channel by default. Open question for this API's deep-dive, not resolved here: how a Beta/Alpha-channel user would actually get to test a genuinely new Inference API feature, if inference itself never follows their channel choice.
4. **Background Workers API** — coherent worker/task framework, not ad hoc threads. Generic execution/scheduling substrate — domain APIs (Reconciliation, Notifications, Proving Grounds' testing, etc.) register work; this API decides how/when it runs. Includes an idle-time execution class (yields to active foreground scans, runs backfill/auto-fix style jobs only when the system is otherwise quiet), not just the io/native/cpu-pure-python routing already established in the Concurrency Model.
5. **Persistence API** (renamed from "Save API" — SQLite-as-canonical-store no longer fits "Save API" as a name; older notes below that still say "Save API" refer to this same API). Two storage mechanisms: (a) a canonical per-user SQLite database (relational, WAL-mode for safe concurrent writes, includes the Search/Query API's FTS5 tables directly — no separate synced copy) holding structured records (vendor/branch data, config, receipt metadata); (b) content-addressable, non-git blob store for raw receipt images — identified by **SHA-256** hash of the original uploaded bytes, computed before re-encoding (not MD5, broken; not SHA-512, unnecessarily large; SHA-256 is the modern standard for exactly this use), purely immutable, no embedded metadata tagging (a metadata-tagging approach was considered and reversed — see Decisions Log), stored as a space-efficient re-encoded copy (WebP or AVIF — one codec, owner-selected system-wide, see Ingestion's Format Normalization) of the original upload rather than the raw bytes as-received — with its own backup targets (B2 + Storj, parallel) and retention-purge enforcement. Excel is no longer storage — it's a generated export/view produced on demand from the canonical SQLite data, with an explicit reimport path (below) for edits to flow back in; "export-only" elsewhere in this document means "not the storage medium," never "no way back in." Every write goes through this API — nothing else touches disk directly. **Sub-package: Historian** (`persistence/historian/`, corrected — no longer a standalone API, see Decisions Log) — an append-only `events` table in the *same* database recording every logical write (table, row, before/after values, actor — worker/LLM/human, program+API version, timestamp), living in the same transaction boundary as the data write itself so both commit atomically together, which two separate services couldn't guarantee. Filtering events by receipt ID produces that receipt's full edit history. **Expanded scope, see `v3-deepdive-29-historian.md`**: Historian also owns a second, narrative track — a quantized, human-readable account of a receipt's entire processing lifetime (every OCR engine's confidence, corroboration outcome, matching/geocoding, the LLM's own deliberation, any flag raised), deliberately lighter-resolution than Logs API's full verbosity and, unlike Logs, genuinely displayable in the webapp — the mechanism that lets a user or moderator remotely see *why* a scan was processed the way it was. Emitted automatically via Execution Core's own per-stage checkpoint wrapper, not scattered calls from every pipeline API. The live `.sqlite` file separately gets periodic day-rotated snapshot checkpoints (backed up like blobs) for fast disaster recovery — that's a recovery mechanism, not the audit trail; the Historian events table is the audit trail. GitHub remains available as an *optional* export/mirror of the events table for anyone who wants free off-site durability or `git log`-style browsing — a feature, not core infrastructure. **Sub-API: Reimport** (`persistence/reimport/`) — ingests a hand-edited exported Excel file the user explicitly re-uploads via the webapp (e.g. after editing their downloaded copy for BIR audit prep), scanned by the Content Security API (#26) on arrival like any other untrusted external file, then diffs it against current canonical state, validates and resolves conflicts against any DB changes since export, then routes the validated result through the normal write path, tagged as a human-via-reimport actor for the Historian sub-package. An explicit, user-initiated upload-and-diff action, never a live sync — stays here under Persistence rather than moving to Ingestion, since its actual job (diff against canonical state, resolve conflicts, apply through the normal write path) is a Persistence-write concern, not an acquisition/normalization one, even though it's conceptually "receiving a file from outside the system" like Ingestion's other channels. First concrete case of a sub-API nested under a core API's package. **Receipt data model**: supports zero-or-more typed reference identifiers per receipt (`type`/`value` pairs — license plate, utility account number, policy/patient ID, etc.) rather than fixed one-off columns, so new identifier types never need a schema change — the registry of *which types are valid* is owned by Architect API (#25), not defined here; Persistence just stores instance values against whatever types Architect has registered. **Excel export generator**: reuses V2's live-formula technique — a print-friendly summary sheet built as Excel formulas pulling from the raw data sheet, rebuilt only when structure actually changes (not on every value edit). **V2's file-open-tolerance requirement (writes must tolerate the target file being open in Excel already) no longer applies and should not be carried forward** — V2 ran locally with the workbook as a live file on the same machine the program wrote to directly, so a user having it open in Excel while the program tried to write was a real, frequent collision. V3's execution core has no direct filesystem relationship with the user's own machine at all: export generates a file server-side, the user downloads their own copy via the webapp, edits *that local copy* in Excel, and explicitly re-uploads it through Reimport when done — there is no file the server and the user's Excel are ever both touching at once, so this entire class of collision is architecturally eliminated, not just handled more gracefully. **Generalized into an Export Framework** (`persistence/exports/`) — the same Provider Registry pattern used everywhere else (rule #5), applied to exports: each export type (general Excel, SLSP summary, audit-package bundle, and any future export a user needs) is a registered export provider consuming the same canonical SQLite data, not a one-off hardcoded feature per format. Modular by design so adding a new export type never requires touching existing ones. **Receipt document type** (OR/SI/CR/Billing Statement, etc.) — a new taxonomy category, owned by Architect's registry like every other typed classification; Persistence stores the instance value per receipt via the same reference-identifier mechanism. Classification logic (how OCR/Inference actually determines which type a scanned receipt is) rolls to the OCR/Inference/Matching deep-dive. **Sub-capability: Archive Sync** (`persistence/archive_sync/`) — the inverse of Ingestion: an opt-in, per-user convenience feature that mirrors a user's processed/archived receipts *out* to an external drive provider (Google Drive first; extensible to others via the same swappable-provider pattern used for Ingestion's Drive-access strategies — worth reusing the same connection/credentials a user already granted for Drive ingestion, rather than asking them to authorize twice, where applicable). One-way sync (internal blob store/Persistence → external folder) — the external copy is a convenience mirror, never a second source of truth, consistent with the same principle that demoted Excel from a storage medium to a generated export (with Reimport as the explicit, user-initiated path for edits to flow back in — never a live sync). The default browsing experience for *all* users (direct-upload included) is the webapp's "My Files" screen (Interface API, built on Search/Query + Persistence) — Archive Sync is strictly additional, for users who specifically want their archive visible in their own external Drive too. **Sub-API: Disaster Recovery** (`persistence/disaster_recovery/`) — owns the actual full-instance restore procedure against the existing blob (B2+Storj) and SQLite snapshot backup targets, distinct from the backup *mechanisms* themselves (already described above) and distinct from Reimport (single-user data reconciliation, not instance-level restore) and Historian (audit trail, not a restore procedure). Genuinely new territory, no V2 equivalent — **full first design pass now done in Persistence's own deep-dive** (`v3-deepdive-13-persistence-api.md` §9): blob-before-SQLite restore ordering, post-restore hash verification against orphaned-reference detection, with partial/single-user restore left as a genuinely open question there rather than assumed either way. **Full design for the entire Persistence API, all sub-packages included, lives in that same document** — this file 01 entry is the summary, not the authoritative detail.
6. **Interface API / Control Panel** — runs as a separate process from execution core; structured GUI + menu/navigation framework (not hardcoded screens); themable; tooltips from day 1; every control documented down to which API it calls. **Webapp lives in the same repo** (`services/interface/webapp/`, same reasoning as the Supervisor staying in-repo — avoids a second CI pipeline/versioning scheme for a solo-dev project), built as part of normal release-clone preparation, not a separate deploy process. Frontend framework choice (React/Vue/Svelte) is an open decision for this API's deep-dive, not picked yet. **Hosting is unified across both modes — Gateway serves the webapp's static build directly in self-hosted AND hosted multi-tenant mode** (corrected from an earlier split that put the frontend on Cloudflare Pages for hosted mode — reverted, see Gateway API entry for why). CDN-like performance is recovered via Cloudflare Cache Rules on the static-asset paths passing through the Tunnel, not a separate hosting product. A future hybrid (Cloudflare Pages serving just the Stable channel as a fast path, Gateway as fallback for other channels) is a legitimate later optimization once there's real traffic data, not a v1 decision. Webapp includes a **"My Files" screen** — the default way any user (direct-upload or otherwise) browses their processed/archived receipts, built on Search/Query + Persistence, not dependent on any external drive integration. **TUI includes an "Active Services" (fleet) screen** — lists every currently-running API instance, which release directory (version-commit tag) each is running from, and its live status; sourced from Health API's Watchdog (per-instance liveness + version/commit, already tracked for exactly this reason) and the Supervisor (which release directory each process actually maps to). **This isn't only a rollout-transition view — in hosted multi-tenant mode, multiple channels running concurrently is a standing state** (each user picks their own channel, so e.g. Stable, Beta, and LTSC instances of the same API can all be genuinely active at once, ongoing, not just during a brief cutover window), and the screen needs to represent that as normal, not as an anomaly. It also still correctly shows the transient rollout case (old draining + new active instance of the same API, both visible during cutover). **Also includes a Telemetrees section** — everything Telemetrees has analyzed/compiled/sent, pulling from Telemetrees' own activity log (signal received → issue created or updated, the dedup decision, a link to the actual GitHub issue). **Version codename ASCII art**: each major version's codename (see Versioning Scheme's Z→A mineral list) has an ASCII art file living in the repo itself (e.g. `assets/ascii/`), keyed by `MM`+codename — small plain text, versioned alongside code like everything else, not the top-level shared-assets folder (which is specifically for large files worth avoiding duplication on). Rendered in two places: the **Boot Sequence loading screen** (see Update API) as a prominent splash while services health-check, and a **persistent header at the top of the TUI's menu navigation**. Both are stateful custom screens, added to rule #1's enumerated exception list. **All codenames' art is retained indefinitely, not just the current one** — a running instance always renders its own version's codename, and since multi-channel concurrent operation is a standing reality (an LTSC user could genuinely be running `x03.xx.xx`/Zircon while `x04`/Yttrium is current elsewhere in the fleet), the codebase needs art for every codename back to at least the oldest actively-supported LTSC version — trivial cost given the files are tiny text, so the simplest safe default is keeping all of them, no pruning needed. Free side effect: a "codename hall of fame" version-history screen becomes essentially free to add later, since nothing needs retrieving from anywhere — it's already all there. **Credits screen**: a deliberately buried settings button triggers a scrolling credits sequence (publisher, owner, developer(s), the codename Hall of Fame, and third-party acknowledgments) — genuinely for fun, but with a real second purpose: it's where a licensed self-hosted install credits its developers to the business that bought it, and it's the natural, low-effort home for **open-source attribution** — many of this project's dependencies (Pillow, ONNX Runtime, Textual, FastAPI, etc.) ship under licenses (MIT/BSD/Apache 2.0) that require their copyright/license notices be included in redistributed software. Once this is being sold rather than just self-used, that's a genuine legal obligation, not just a nice touch — the credits screen is a natural, already-planned place to satisfy it rather than needing a separate compliance mechanism. **Localization/i18n**: no dedicated sub-API — treated as a cross-cutting concern of this API (string externalization + locale-aware formatting) to be structured at this API's own deep-dive, the same way theming isn't its own sub-API either.
7. **Matching API** — vendor / TIN / address / franchise-vs-franchiser matching; fuzzy matching (rapidfuzz or alternative, TBD). Owns the actual matching/lookup logic and the "two-way" fuzzy match (extracted candidate against the DB forward, plus known vendor names/aliases scanned against the entire raw OCR text in reverse, scoped to a contextually-plausible subset to bound cost) — consumes the Vendor/Branch directory data rather than owning how it's learned/maintained (see Architect API #25, which now owns the Vendor Directory's schema, Wikidata bootstrap, aliasing, category taxonomy, and global contribution/audit mechanism).
8. **Geo/Address API** — geocoding source(s) for address validation/normalization. Default providers: LocationIQ + Mapbox (both free at expected scale, independent underlying data sources for genuine corroboration). Self-hosted Nominatim (PH-only OSM extract, on an Oracle Cloud Always Free VPS) available as an unlimited-throughput option for scale or fully cloud-independent self-hosted installs. Response caching (keyed by normalized query, in the same canonical SQLite database) stretches every provider's free tier. Extended to the Provider Registry pattern: multiple providers run in parallel and cross-checked, mirroring OCR's corroboration model — plus a distinct multi-candidate axis within a provider (see Claude Code Audit Findings: search several plausible vendor/address strings ranked by frequency across OCR readings, not just the single best guess).
9. **Reconciliation API** (renamed from "Reconciliation & Learning API" — the "Learning" half moved to Architect API #25, keeping it in the name was stale) — reconciles old records when vendor/branch data changes (propagating corrections to affected receipts in the canonical database — not "editing Excel directly," since Excel is a generated view/export, not the storage medium; the path for external edits to flow back in is Persistence's Reimport sub-API, an explicit user-initiated upload-and-diff step, never a live sync — see Persistence API). Manages the underlying 2-page structure that the Excel export reflects (RESOLVED: V2's second page is a live-formula summary/print sheet pulling from the raw data sheet — see Persistence API's Excel export generator notes). Domain logic that runs on the Background Workers API's execution substrate, not a competing scheduler. Consumes learned/taxonomy data from Architect API (#25) rather than owning the learning mechanism itself. **Full design in this API's own deep-dive** (`v3-deepdive-17-reconciliation-api.md`): a concrete twelve-check inventory, complete (VAT math, TIN format, date plausibility, account outliers, semantic duplicates, vendor-group/items-vendor mismatches, BIR completeness, orphaned/missing archive-reference detection, an address/vendor geo-cross-check applying Geo/Address API's own capability retroactively to old receipts (`docs/PRINCIPLES.md` §1.9), and ATP validity checking), correction propagation via Architect change-events, and bulk propagation now genuinely wired through Execution Core's own checkpointing mechanism rather than just named as the right pattern.
10. **Notifications/Inbox API** — in-app inbox notifications; feeds owner alerts (break-glass access grants), client alerts (run complete/errors), and future reprocessing-on-upgrade prompts. Currently in-app only — extending it with outbound channels (email/SMS, for a client not actively looking at the app) is implementation scope for this API's own deep-dive, not a new API.
11. **Tool Call API** — central tool registry (read-only vs. mutating tools, per-context enabled subsets) that the Inference API's tool-calling orchestrator invokes on the LLM's behalf; includes a web search tool for vendor research (TIN lookup, branch existence).
12. **Auth & Tenancy API** — passwordless authentication (SSO/OIDC — Google first, uses only non-sensitive scopes for login: email/profile/openid, which is the light Google verification tier, no CASA audit, a few weeks of review — plus passkeys, email one-time codes, and SMS one-time codes, with composable 2FA on any of them; **no local password authentication exists anywhere in this design, under any circumstance**, a deliberate, explicit choice — see `v3-deepdive-05-auth-tenancy-api.md` §4), server-side sessions with httpOnly cookies, owner/staff/client roles, break-glass access grants, `tenancy_mode` (single/multi) config, per-user folder/repo isolation. DOMTRI's hosted service uses one verified OAuth client for login (removes V2's Testing-mode 100-user cap and 7-day token expiry entirely for approved scopes); self-hosted installs can stay in unverified Testing mode indefinitely, which is fine for a single-user/small-team install well under the 100-user cap, or configure their own via the Setup wizard. Owns session/identity *mechanics* — the user-facing self-service surface built on top of them (device management, account recovery, SSO changes) lives in Account Guardian API (#28) instead, to keep this API's scope infrastructural/owner-side rather than mixing in a user-facing product surface.
13. **Logs API** — comprehensive, verbose operational logging covering every subsystem (OCR engine outputs/timing, LLM prompts/responses/tool calls, preprocessing steps, worker activity, errors), structured/queryable, feeds the Interface's live run monitor. Distinct from the Audit API (security actions) — this is operational trace. Contains real receipt content, so read-access follows the same per-user permission rules as the Persistence API — but storage does NOT go through Persistence's Historian sub-package (see Decisions Log: logs are gitignored, rotated flat files with their own retention policy, not an events table or git history). Always captures full tracebacks on failure, never just `str(e)` — async/threaded failures are hard enough to debug without losing the traceback. Configurable verbosity tiers, not just a single max-verbosity mode.
14. **Audit/Event Log API** — canonical, append-only log of privileged/security-relevant actions: break-glass access grants, global vendor contribution reviews, config/role changes.
15. **Ingestion API** — acquisition and assembly of source receipt images from multiple channels: Google Drive (kept for compatibility — some users specifically prefer feeding receipts in via a watched Drive folder over the webapp), direct web upload, and an in-browser scanner (camera capture → corner/edge detection → perspective correction) with a panorama/stitching mode for long receipts. Hands finished images to the Preprocessing API; does not itself do OCR-oriented image transforms. Every incoming file is scanned by the Content Security API (#26) before reaching Preprocessing/OCR — Ingestion calls it, doesn't own the scanning logic itself (Persistence's Reimport sub-API needs the same scanning for its own uploads, so it lives in one shared place, not duplicated). **Sub-API: Format Normalization** (`ingestion/format_normalization/`, corrected from an earlier "sub-capability" mislabeling caught during a corpus-wide sweep — it has its own real package path and depth comparable to Historian or Reimport, given its own full dedicated document, `v3-deepdive-42-format-normalization.md`) — accepts a wide input universe: **Pillow already natively covers essentially every image format in existence** (JPEG, PNG, WebP, GIF, TIFF, BMP, ICO, PSD, PPM, PCX, EPS, and 30+ more, plus **native AVIF read/write built directly into Pillow itself** — no separate plugin needed, a change from older guides that still reference `pillow-avif-plugin`) — the *only* gap in Pillow's core is HEIC/HEIF (kept out for HEVC licensing reasons), which is exactly why `pillow-heif` is the one necessary plugin on top of it, not a separate solution. Also handles PDF (iPhone/scanner-app exports, via `PyMuPDF`/`fitz`) and .zip archives (bulk-uploaded scan batches, via Python's built-in `zipfile`). **One codec for the whole install, owner-selected** (WebP or AVIF, not both) — a single system-wide config value, never a per-user/tier lever; the content-address hash is computed over the original uploaded bytes, before re-encoding, decoupled from Persistence's own `BlobLocation`-mapped physical storage. Normalization output branches two ways from one common source, not sequentially: (a) archival re-encode → hashed → stored as the permanent Persistence blob, and (b) fed separately to Preprocessing's pipeline. Full design — including the real CVE history on `pillow-heif` that keeps these libraries on Proving Grounds' update-testing radar, and the 3.16 selective zip-remediation interaction with Content Security — lives entirely in that dedicated document now, not summarized further here. **Google Drive access uses a swappable credential-provider interface (Provider Registry pattern, rule #5), with service account as the only currently-usable strategy and per-user OAuth built in as a second strategy behind the same interface — ready to activate once Google's app-verification process clears, not available yet, not a current alternative to choose between.** Service-account access (a user shares their receipts folder with a designated service-account email, the same action as sharing a folder with a colleague) is mandatory for now: per-user OAuth for sensitive/restricted scopes requires passing Google's OAuth app-verification process before it can be offered to real users at all, which service-account access simply doesn't need (no 100-user Testing-mode cap, no 7-day token expiry, no CASA-audit dependency) — that's the actual, practical reason service account is what works today, not a preference. Per-user OAuth remains the intended eventual default once verification clears — it's the model that matches how every other user-facing integration in this project works, and most users will expect it — so it's built as a fully-implemented second credential-provider strategy behind the same interface from day one rather than deferred until verification clears and bolted on afterward. Both strategies implement the same internal credential-provider interface, so flipping the default once OAuth becomes usable is a config change, not a rewrite — the Webhook Subscription Manager below is already written this way ("works identically regardless of whether the underlying Drive credential is a service account or a user OAuth token"); every other consumer of Drive access needs to hold to that same discipline, and this correction is a reminder to check the OCR/Preprocessing/Inference deep-dives' own external-service integrations for the same "swappable, never hardcoded to one auth mechanism" discipline rather than assuming it was already followed everywhere. DOMTRI's hosted service and self-hosted installs both use service account today; per-user OAuth switches on for whichever deployments want it once verification is through, no architectural change needed at that point. The onboarding step (share-folder-with-this-email today; the OAuth consent screen once available) is surfaced clearly in Setup/Ingestion settings. **Owner controls which ingestion sources are active at all**, not just which Drive credential strategy is in use — each source (Drive, direct upload, in-browser scanner, any future channel) is an independently enableable Provider Registry entry, same pattern as OCR's engines and Preprocessing's variant kinds; disabling a source the owner doesn't want offered is a config toggle, not a code change, and this modularity is exactly what keeps adding a future source (email-in, another cloud drive provider) from ever requiring touching the sources already in place. **Sub-API: Webhook Subscription Manager** (`ingestion/webhook_manager/`) — generic, provider-agnostic push-notification subscription handling (not specific to Google Drive — the same mechanism would handle OneDrive/Microsoft Graph or any future push-capable source via a different provider adapter, same Provider Registry pattern used elsewhere); works identically regardless of whether the underlying Drive credential is a service account or a user OAuth token. Registers/renews subscriptions with tracked expiry, proactively renews ahead of lapse via a Background Worker (idle-time class) — renewal creates a new channel ID, not the same one, so the safe sequence is register-new-then-confirm-active-then-deregister-old, never stop-then-start, to avoid a delivery gap. No true "ping" exists for these providers (no status endpoint to call) — this inferred-health mechanism is named **"Webhook Circadian"**, distinct from Watchdog (which proves *our own* process is alive via kicks): Circadian infers a *third party's* delivery rhythm is still healthy from timing — proactive renewal against the known expiry, plus the fallback poll surfacing any changes a healthy webhook should have already delivered. Receives the actual webhook callback via Gateway, handles provider-specific quirks (e.g. Drive's empty-body callback requiring a follow-up `changes.list` call), and emits a "new file available" event for Execution Core to consume — batching/coalescing those events into runs is Execution Core's job, not this sub-API's. Configurable fallback poll interval (daily is fine, not just hourly — its only job is catching a rare silent webhook failure, not being a primary mechanism) as a safety net alongside the push trigger.
16. **Gateway API** — the FastAPI REST/WebSocket layer in front of the gRPC core; exposed via Cloudflare Tunnel at `resibo.renovait.qzz.io` (single origin — see below, `api.` subdomain corrected from required to reserved-for-later). **Serves the webapp's static build in every deployment mode, not just self-hosted** — corrected after realizing Cloudflare Pages' single/branch-deployment model doesn't cleanly support serving different frontend versions to different users based on an individually-chosen channel, and having frontend-version-routing (Pages) and backend-version-routing (Gateway/Supervisor) as two separate mechanisms risks them disagreeing — a user's Beta-channel backend paired with a Stable-channel frontend is a real, nasty bug class, not hypothetical. Reusing Gateway's existing per-user-channel routing to also serve the correct frontend bundle guarantees frontend/backend version pairing stays consistent by construction. **Single-origin correction**: since webapp and API now share one process, a separate `api.` subdomain became vestigial — dropped as a v1 requirement (see Branding & Naming). The webapp calls API routes (e.g. `/api/v1/...`) as relative same-origin paths, not a cross-origin URL — eliminates CORS configuration entirely and simplifies session cookies (`SameSite=Lax` is fine same-origin; cross-origin would need `SameSite=None; Secure`, with its own browser-compatibility quirks). Any rate-limit differentiation between static assets and API calls is handled via path-based rules, not a subdomain split. Handles direct file upload: browser POSTs the file → Gateway authenticates (session cookie) → forwards over internal gRPC to Ingestion API, which routes it through the Content Security API before hashing/storing the blob and emitting a trigger event for Execution Core's usual debounce-coalescing window. Direct upload is the simplest of the three ingestion channels mechanically — no push/poll uncertainty, no third-party reliability question; the upload arriving *is* the trigger, with none of Drive's Webhook Circadian/fallback-poll complexity needed. **Security posture, not solely delegated to Cloudflare**: Cloudflare's Tunnel provides real network-edge DDoS protection, but Gateway still owns its own request rate-limiting and input validation as defense-in-depth — never relying on one vendor as the single point of protection. File-content scanning is the Content Security API's job, not Gateway's — Gateway's job is the network/request layer.
17. **Billing & Subscription API** — payment/subscription management for **hosted multi-tenant customers only**; GCash and bank transfer support via a Philippine payment aggregator (PayMongo or Xendit — decision pending), tied to performance-tier config profiles. **Explicitly does NOT handle self-hosted licensing** (corrected after a real design flaw was caught — see Keymaster in Branding & Naming, file 2): putting license-validation logic inside this API would mean it ships inside every self-hosted release clone, sitting on the exact machine it's supposed to be checking, fully readable and patchable by the person it's meant to validate — a check that isn't a check. Self-hosted licensing is a completely separate, closed system.
18. **Health API** — two layers: (a) status (service up/down, queue depth, per-instance resource utilization, external-dependency reachability), (b) live diagnostic, reusing the bench suite's empirical wall-time/CPU-time/RSS classification technique continuously against real traffic instead of only at bench time — flags soft degradation (e.g. a normally-CPU-bound engine going network-bound) not just hard failures. Feeds Notifications/Logs/Audit; primary consumer is staff/owner via the TUI; gates the Update API's health checks during rollouts. **Sub-API: Watchdog** (`health/watchdog/`) — liveness monitoring distinct from crash detection: each service proves it's alive via periodic kicks, auto-triggers a restart if silent past a timeout (a hung-not-crashed process is invisible to plain process-status checks). Also tracks which version/commit each currently-running service instance is on, given A/B hot-swap — version/commit info rides on the heartbeat/health-check response specifically, not on every business response (cheap either way at this call volume, but no reason to pay it on the hot path).
19. **Search/Query API** — FTS5 and structured search tables living directly in the Persistence API's canonical SQLite database (not a separate synced copy) — full-text OCR search included from v1, not deferred. Staff cross-user search is break-glass-gated, same mechanism as staff touching client data.
20. **Migration API** — every persisted structure (config, vendor/branch data, database schema) carries a `schema_version`; a migration registry chains N→N+1 steps rather than jumping versions directly. Migrations write through the Persistence API, so each migration is automatically an atomic, revertable event via its Historian sub-package — no separate rollback machinery needed. gRPC `.proto` versioning follows protobuf's own backward-compatible discipline (only add fields, never remove/renumber).
21. **Update/Deployment API** — no-downtime updates via **named, multi-channel release directories** (`<version>_<commit-hash>`), garbage-collected rather than a fixed slot count — supports LTSC/Stable/Beta/Alpha channels (user-selectable) plus an owner-only Latest-Commit channel existing side-by-side. **In hosted multi-tenant mode, multiple channels can be genuinely, deliberately active simultaneously as a standing state — not just transiently during a rollout.** Since each user can pick their own channel, a running deployment can have several release directories concurrently serving real traffic at once (one per channel currently in use by at least one user) — this is ongoing normal operation, not a brief cutover window. Every update is a genuinely fresh `git clone` into a new named directory — never a pull, never in-place mutation. **For self-hosted installs specifically, this clone is gated by license validation against Keymaster** (a completely separate, closed external system — see Branding & Naming for full design), not by anything in this repo: the code repo itself must be private, and Update API calls out to Keymaster for a short-lived, scoped clone token before each attempt — a lapsed license just means the *next* clone fails at GitHub's own auth step; the currently-running instance is entirely unaffected (fail-open, never locks a customer out of their own already-running data). A **Runtime Manager/Supervisor lives outside every release clone at the top level** (a bootstrapping necessity — see Decisions Log) and owns launching each service from the correct per-user-channel release's own per-service venv (self-hosted single-tenant mode simplifies to one active release, one marker, same as before), health-gating cutover via the Health API, and driving rollback; it has its own separate, more conservative update path. **The same health-gating logic also defines the Boot Sequence — cold start, not just rollout cutover, named explicitly since it deserves real design**: on program launch, Supervisor determines which release to run, launches each service in dependency order (e.g. Persistence before Execution Core, which depends on it), waits for Watchdog to confirm each service's first successful health check, and only then lets Interface API's loading screen hand off to the main TUI — a service that fails to come up within a timeout surfaces clearly (Review/Flagging, or Telemetrees for a genuine system-level fault) rather than silently hanging. **Exception: the Inference API never multiplies per channel — see its own entry.** A Background Worker (idle-time class) garbage-collects unused old releases past a retention window, always keeping the current release plus at least one prior for rollback safety. Includes channel selection (`update_channel`, independent of `dependency_testing_opt_in`) for the beta testing program — see Decisions Log for full shape. **Sub-API: Proving Grounds** *(codenamed, `update/proving_grounds/`)* — the general-purpose candidate-testing mechanism, not dependency-specific: clone a candidate into an isolated release directory (reusing Update's own release-directory machinery, which is why this stays under Update rather than moving to Telemetrees), run it through Health-gated checks and the bench suite's regression comparison, return pass/fail plus diagnostic data. Proving Grounds doesn't know or care *why* it's testing something — two distinct callers request tests from the same mechanism rather than each reinventing it: (1) program-version channel candidates (beta/alpha channel promotion) request a test directly as part of normal channel-based rollout; (2) Dependencies Warden (under Telemetrees) requests a test when it flags a program-important dependency pre-release, then takes the result back to decide what to report onward. A registry of every external dependency (shared with the Setup API for initial install) lives here too, since it's install/deployment bookkeeping, not diagnostic monitoring. For the hosted multi-tenant service, participation in the dependency-bump-testing pool specifically is opt-in per install (self-hosted installs, it's the owner's own call) — not silently applied to real customer runs without consent. Model/dependency downloads (including from Hugging Face, with token-auth support for gated models) are multithreaded/async, not a single blocking sequential fetch.
22. **Review/Flagging API** — the curated, severity-tiered layer on top of the Logs API's raw firehose. A flag has a lifecycle: created by low-confidence OCR/Matching/LLM scoring (or a reimport conflict) → assigned a severity tier → sits in a review queue → resolved or dismissed by staff or the client → resolution recorded. Powers an in-depth per-receipt audit screen (how it was scanned, the different engine readings, what the LLM concluded and why it flagged) by pulling the relevant slice of Logs API data into a readable view — not a redesign of Logs, a workflow layer built on it. **This is also the system's general in-browser edit entry point**: a flag or a Notifications quick-action button deep-links directly into an edit form for the specific field/row, writing through the normal Persistence write path immediately — no separate "inline-edit grid" feature needed. The flag *taxonomy itself* (VAT math mismatch, malformed TIN, implausible date, orphaned/missing archive references, account/category outlier, duplicate row, mislabeled vendor group, items-vendor mismatch, reimport conflict, BIR completeness, malicious/unsafe content detected — from the Content Security API — originally sourced from V2's `reconcile.py` plus fresh BIR-specific and security additions) is now defined in Architect API's read registry (#25) rather than owned here — this API owns the flag *lifecycle*, not the taxonomy definitions.
23. **Setup API** — the first thing a user interacts with; direct fix for V2's `setup.bat`/`setup.sh`/extra `.ps1` helper-script sprawl. **Distribution model**: a GitHub Release per OS is a thin ZIP containing only the setup script (bootstrap), not a source snapshot — the setup script performs the *first* real `git clone` into a named release directory, then hands off to the Setup API code now present inside that clone. Setup API then builds the **top-level directory structure outside every release directory entirely** — config, default data folder paths, models/downloadable assets, and the `start.bat`/`start.sh` launcher all live as siblings, never nested inside any release clone, so user data and shared assets are architecturally unreachable by any future update/clone operation. Owns environment/hardware detection (shared detection logic with Health API), dependency installation (shared Proving Grounds with Update API — see #21's sub-API note), and a first-run config wizard (tenancy_mode choice, initial owner account creation via Auth API using any of its four passwordless methods, run-on-startup/Tunnel Exposure/billing all offered as genuinely skippable steps — **no forced tier selection**, that phrasing corrected out — plus a Google Drive config-restore offer if the SSO'd account has a previous instance's encrypted config backed up), TUI-driven via the same menu-data pattern as the rest of the interface. **Full walkthrough — every step, what it asks, what it does, how — in this API's own deep-dive**, `v3-deepdive-11-setup-api.md` §7. Explicitly idempotent/safely re-runnable by design — that re-runnability, not more helper scripts, is the actual fix for V2's root problem. A self-referential script must never try to move/delete itself while running (fragile, especially on Windows with locked executing files) — the setup script's last action hands off to Setup API's own Python-level finalize routine for any remaining file operations, not a batch/shell self-move trick.
24. **Execution Core API** *(`services/execution_core/`)* — the actual pipeline "running loop," formalized late in this planning process despite being one of the most important APIs (V2 never had a named equivalent, just an unformalized `daemon_loop`+`run_once`). Owns the run scheduler (per-user/global concurrency limits, `run_id`/`user_id` context threaded through every downstream call — already decided earlier, now with a formal owner), pipeline sequencing (Ingestion → Preprocessing → OCR → Matching → Geo → Inference → Persistence write [logged via its Historian sub-package] → Review/Flagging on low-confidence results → Notifications on completion), and applies the active performance-tier profile's knobs to a given run. Its gRPC contract is what Interface/Gateway call to start a run and stream progress — the front door for triggering real work, distinct from the Supervisor (which only ever launches processes, never receipts). Ordinary versioned code, lives in every release clone with its own per-service venv like every other service. Full design detail in Decisions Log: per-stage checkpointing for resumable retries, an explicit state machine, fine-grained cancellation, bounded-retry-with-escalation, hybrid push/poll ingestion triggering, and fine-grained Watchdog integration.
25. **Architect API** *(`services/architect/`)* — thematic pair to Persistence's Historian sub-package (Historian records what changed to instance data; Architect defines what's *allowed to exist* system-wide), created after noticing the same "extensible typed thing" pattern independently reinvented five times across this plan (flag taxonomy, reference-identifier types, category taxonomy, tier profiles, menu-data schema, vendor learning). Owns schemas/taxonomies/the learning mechanism itself — **never actual instance data**, which stays exactly where it already lived (a vendor's real TIN in Matching's data, a specific flag on a specific receipt in Review/Flagging, a user's actual tier assignment in Billing). Two submodules:
    - **Read (`architect/registry/`)** — the live, queryable definitions every other API consumes instead of hardcoding its own: the flag-type taxonomy (Review/Flagging), reference-identifier types (Persistence), category taxonomy (Matching/Inference), tier-profile definitions (Billing/Execution Core), the menu-data schema (Interface). A future Claude Code session (or any tooling) can query this registry directly to know what currently exists, instead of re-deriving it by reading source cold.
    - **Write (`architect/temporal_learning/`)** — the actual learning mechanism, subsuming what was previously described piecemeal under Matching's Vendor Directory and Reconciliation's "Learning" half: Wikidata-seeded global bootstrap, local/global vendor layering and alias accumulation, category-default learning, and the global contribution review flow — implemented as a plain moderation-queue table (`contributions`: old/new values, status pending/approved/rejected, reviewer, timestamps) in the same queryable database, **not git** (corrected — see Decisions Log for why git was dropped from this design). Contribution proposals are LLM-prescreened, staff-reviewed for flagged items, then applied to the live global registry on approval.
26. **Content Security API** *(`services/content_security/`)* — deliberately scoped narrower than "security" generically, to avoid becoming a catch-all that swallows Auth's identity/session security or Gateway's network-layer concerns, which stay exactly where they are. Owns verifying that untrusted external content is actually safe before anything else in the system trusts it: real file-type verification (checks actual content via file signature/magic bytes, not the extension or client-supplied MIME type, both trivially spoofable — directly answers "a non-image uploaded as an image"), malware/exploit scanning (swappable provider per rule #4/#5 — ClamAV as an open-source default, a cloud AV API as an alternative), and polyglot/embedded-payload detection (a file valid as one format while smuggling another format's payload inside it). **Archive-bomb detection** (zip files specifically): a container-level check using `zipfile`'s own metadata (`infolist()` — exposes each entry's compressed and uncompressed size) *before* any extraction — rejects based on per-entry compression ratio, cumulative uncompressed total, entry count, and nesting depth, all without ever unpacking a hostile archive. **Two-pass model, not a single scan**: (1) container-level safety check on the archive/PDF/etc. as a whole, (2) after Ingestion's format normalization extracts/renders individual files, each one gets its own normal file-type/malware/polyglot pass too — a bomb-free archive could still smuggle one bad file among good ones. Called by every entry point that accepts untrusted external content — Ingestion API (all receipt channels) and Persistence's Reimport sub-API (uploaded Excel files) — one scanner, not duplicated logic per caller. **On rejection**: dropped cleanly, logged via Logs/Audit, and creates a high-severity Review/Flagging entry ("malicious/unsafe content detected") — immediate dual notification via Notifications (user gets a general "couldn't be processed" message, never scanner internals; staff/owner get full detail as an urgent alert, since a real hit may be an actual attack attempt). Staff verdict, via Review/Flagging's existing resolution mechanism: confirm-malicious (permanent rejection + a formal warning logged to the Audit API against the user, since that's a genuine privileged action worth a queryable trail for any future repeated-violation handling) or override-false-positive (releases the file back into the normal pipeline). **Scope note**: this API guards against illegitimate/malicious files, not against a paying user simply burning their own run budget on legitimate-but-useless files — that's a subscription-tier/self-service concern, not a security one, and is explicitly out of scope here.
27. **Telemetrees API** *(codenamed, `services/telemetrees/`)* — deliberately its own top-level API, not a sub-API of Update, for the same reason Architect got pulled out on its own: it spans multiple APIs (Health, Update, Dependencies Warden) rather than naturally belonging to one, so bolting it onto any single one would recreate the "wrong owner" problem Architect exists to prevent. **Sub-API: Dependencies Warden** *(codenamed, `telemetrees/dependencies_warden/`)* — continuous automated monitoring of every tracked dependency for stable AND beta/alpha/RC pre-release activity, surfacing newly detected releases/changelogs for the "is this program-important" judgment call. When something is flagged, Dependencies Warden **delegates the actual test execution to Update API's Proving Grounds** (see #21) rather than running it itself, then takes the pass/fail result back and decides what to report onward through Telemetrees' compile-and-report pipeline. This keeps Dependencies Warden purely "watch, judge, delegate, interpret, report" — a clean fit for a Telemetrees sub-API — while the actual candidate-build-and-test mechanics stay with Proving Grounds, since that's deployment machinery Dependencies Warden would otherwise have had to duplicate. **The crash-handler analogy, precisely stated**: this is the rough equivalent of a game's crash-handler telemetry system — except this program is designed to basically never hard-crash (graceful degradation is a standing principle throughout this plan), so Telemetrees' real job is compiling *diagnosed errors and degradation signals* into trackable issues, not catching unhandled exceptions. **Consolidates several already-scattered "report this to developers" pathways into one real pipeline**, rather than each API inventing its own ad hoc reporting mechanism (the same anti-pattern Architect was created to stop, applied to diagnostics instead of taxonomies): Health API's soft-degradation detections, Update API's failed-rollout/auto-rollback events and failed bump-test reports, and Dependencies Warden's own flagged pre-release features all route through this one pipeline instead of each reporting independently. **Mechanism**: takes a raw diagnostic signal, compiles it into a well-formed GitHub Issue (title, description, relevant logs/diagnostic data attached) via a swappable issue-tracker adapter (GitHub as the obvious default given this repo, kept swappable per rule #4/#5 rather than hardcoded, in case a GitLab/other tracker is ever needed). **Authenticated via a GitHub App, not a personal access token** — a PAT is the faster path to something working during initial development, but is tied to one person's account (breaks if they leave, rotate 2FA, etc.) and typically carries broader scope than needed; a GitHub App is org-owned, installable on just the specific repo(s), scoped precisely to `issues` read/write and nothing else, and issues short-lived auto-rotating installation tokens instead of one long-lived static secret. Credentials live in the same top-level, outside-every-release-clone config location already established for other secrets (never committed, never inside a release clone) — self-hosted installs that opt in configure their own target repo and credentials if they want Telemetrees filing issues in their own fork rather than DOMTRI's canonical repo, consistent with the swappable-adapter design above. **Deduplication is a real, load-bearing requirement, not an afterthought**: the same underlying problem recurring (e.g. a soft-degradation pattern happening daily) must group into one issue that gets updated/commented on, never spawn a flood of duplicate issues — the same class of problem error-tracking tools like Sentry solve, via fingerprinting the underlying signal rather than the individual occurrence. **Distinct from Review/Flagging by audience, not just mechanism**: Review/Flagging is for end-user/receipt-level issues needing staff or client resolution, living in the in-app queue; Telemetrees is for system/code-level issues needing developer attention, living in GitHub Issues — different problems, different destinations, never conflated. **Privacy/consent, reusing the Beta Program's existing discipline**: only DOMTRI's own canonical instances have this wired up by default; any other install (self-hosted, or an opted-in hosted customer) must explicitly opt in, and any diagnostic data that leaves the install must be scrubbed of receipt/financial content first — the identical scrubbing requirement already established for the Beta Testing Program's crash reports, reused rather than reinvented. **Exposes its own queryable activity log** (not just fire-and-forget issue creation) — every signal received, whether it was deduplicated into an existing issue or created a new one, and a link to the actual GitHub issue — this is what backs the TUI's Active Services screen's Telemetrees section.
28. **Account Guardian API** *(`services/account_guardian/`, name tentative — flag if you want something else)* — the user-facing privacy and account security center, deliberately on the user's own side first rather than the server owner's. Owns: device/session management (view and remove active sessions), account recovery (regaining access to a lost SSO/passkey/email/SMS method — never a password reset, since no local password ever exists, `v3-deepdive-05-auth-tenancy-api.md` §4), and data-privacy requests (export, deletion — RA 10173/Data Privacy Act relevance given real financial data + TINs are in scope, plus versioned consent tracking for Terms of Service/Privacy Policy, `v3-deepdive-06-account-guardian-api.md` §7). Consumes Auth & Tenancy's (#12) session/identity primitives rather than duplicating them — Auth owns the mechanics, this API owns the user-facing self-service surface plus the genuinely new data-subject-rights territory Auth never covered. No V2 lineage; genuinely new. **Full design in this API's own deep-dive**: the request/approval flow for deletion (a real grace period + Background Workers-driven sweep, no longer just "immediate vs. grace period" as an open question), how it interacts with Billing (a `BILLING_HOLD` stage before deletion can proceed), and break-glass notifications correctly staying a Notifications API job, not blurred into this one.
29. **Accounting Sync API** *(`core/accounting_sync/`)* — surfaced as a genuine blind spot during a corpus-wide sweep, never previously mentioned anywhere in this plan. Live, credentialed, ongoing push of processed receipts into a user's own QuickBooks/Xero account as expense/bill records — deliberately one-way (push only, no read-back), a real bidirectional-sync-against-an-external-system's-own-schema problem explicitly deferred rather than attempted now. One-time, no-OAuth file exports for the same two platforms live separately, as new Export Framework providers (#5), not here — this API owns only the live-connection case. **Full design in this API's own deep-dive** (`v3-deepdive-50-accounting-sync.md`): `AccountingSyncProvider` Protocol (QuickBooks/Xero), per-user (not system-wide) OAuth connections, encrypted token storage kept structurally separate from queryable business data, and push-eligibility gated on a receipt being fully processed and un-flagged.
30. **Status Page API** *(`services/status_page/`)* — surfaced as a genuine blind spot during a corpus-wide sweep, never previously mentioned anywhere in this plan. A public, unauthenticated uptime/incident page for DOMTRI's hosted service — genuinely its own small, infrastructurally-independent app (not a webapp screen, not a Gateway route), specifically so it stays reachable when the main product is having problems. Doesn't apply to self-hosted installs at all. **Full design in this API's own deep-dive** (`v3-deepdive-51-status-page.md`): staff-authored incidents (never auto-generated from a health-check flip), coarse public-facing component groups that never leak internal API names, and its own small local cache so it can render a last-known state even if the core gRPC fleet is genuinely unreachable.
31. **Support Ticketing API** *(`core/support_ticketing/`)* — surfaced as a genuine blind spot during a corpus-wide sweep: Auth's own break-glass `reason` field always referenced "a support ticket ref" as if such a system existed, but nothing ever actually built one. A real, deliberately simple ticket lifecycle (open → in progress → resolved → closed), no complex routing/SLA machinery at this project's actual scale. **Full design in this API's own deep-dive** (`v3-deepdive-52-support-ticketing.md`): a `related_receipt_id` field letting staff jump straight to a receipt's own detail screen and full Historian narrative from within a ticket, and a real (if soft) integration point back into break-glass's own reason field now that there's something real for it to reference.
32. **Agent Control API** *(`core/agent_control/`)* — programmatic access to a running instance for AI agents and automation (Claude Code specifically, designed generally). Provides an MCP server and a headless/scriptable CLI, both reusing Tool Call API's own existing `READ_ONLY`/`MUTATING_STAGED` categorization plus a new `DEV_OBSERVABILITY` category added there specifically for this API's own real, verified tools (run status, system health, Historian narrative, log tailing, dependency status — each a wrapper around an existing RPC, not invented). An agent is never more capable than the human who authorized it, and can never carry `owner`-level permissions regardless of who issues its token. **Full design in this API's own deep-dive** (`v3-deepdive-55-agent-control-api.md`), with its own extracted sub-API for genuinely complex tests (`v3-deepdive-56-test-orchestration.md` — crash-isolation testing, full pipeline-integration test runs, environment reset, all MCP-callable rather than one-off scripts) that also adds a real, structural safeguard against synthetic test fixtures being mistaken for real receipt scans.
