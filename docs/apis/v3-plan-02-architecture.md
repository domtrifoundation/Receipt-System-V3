# V3 Plan (3/5: ARCHITECTURE — cross-cutting concerns, repo hygiene, ONNX inventory, concurrency model, versioning)

**Companion files:** `v3-plan-00-index.md` · `v3-plan-01-core-apis.md` · `v3-plan-03-decisions.md` · `v3-plan-04-v2-audit-findings.md`

## Cross-cutting concerns (apply to every API above)

- **Concurrency model — RESOLVED, see dedicated "Concurrency Model per API" section below.** Three buckets established (async I/O, native/GIL-released, no-GIL-candidate-pure-Python), applied to every API individually rather than reinvented per-API.
- **Process boundary**: what lives in the core execution process vs. control panel vs. inference server(s) vs. worker pool.
- **IPC**: how core/interface/inference-server/workers talk to each other, given they're now deliberately separate processes.
- **Config/settings surface**: one schema, one source of truth, versioned.
- **Failure isolation**: a crash in one API (e.g. an OCR engine) must not take down the run.
- **Repo hygiene**: branching, commit discipline, and where V3 lives relative to V2 (fresh repo vs. branch).
- **Startup Sequence — a designed, documented flow, not a new API.** What launches everything and verifies it's actually ready before the TUI goes interactive is an orchestrated sequence across APIs already built, not a new bounded domain — a new API here would just be a thin wrapper calling into three others. Distinct from Setup API (one-time first-run configuration) — this runs on *every* launch. The sequence: (1) Supervisor bootstraps, reads the active-release marker(s) per channel, begins launching each service from the correct release's per-service venv; (2) **launch respects a real dependency order, not parallel-launch-and-hope** — foundational/data-layer services (Persistence, Architect's registry) come up before anything depending on them; (3) each service reports genuine readiness (not just "process exists" — e.g. Inference finishing a model load) via Health API's existing status layer; (4) the TUI's loading screen shows real progress against this (e.g. "14/24 services ready"), not a generic spinner; (5) a service failing to report ready in a reasonable window routes through the same Watchdog-retry/Telemetrees-escalation mechanisms already built for exactly this — a "won't start" pattern is a genuinely diagnosable issue, not a special case; (6) once everything required is ready, the TUI transitions from loading screen to normal interactive state.
- **Version codename ASCII banners** — one file per major-version codename, keyed to `MM` only (so every `x03.xx.xx` release reuses the same Zircon banner without regeneration), stored as a plain static asset under Interface API's scope (branding, not learned/taxonomy data — not Architect's territory). Displayed at (a) the startup loading screen, large, alongside the progress indicator, and (b) persistently at the top of the TUI's main menu navigation, smaller/header-style. **Old codename files must be retained, not just for nostalgia** — LTSC exists specifically so a channel can stay on an older major version long-term on purpose; an LTSC install genuinely still on `x02.xx.xx` needs its own correct banner, not the current generation's. Retention is a functional requirement flowing from LTSC's own purpose; a "Version History" screen showing the full codename lineage becomes a free bonus once that retention already exists for functional reasons.

## Repo Hygiene Rules (enforced, not aspirational)
*(binding rules for this codebase — a PR/change that violates one of these is treated as a bug, not a style nit)*

1. **NEVER hard-code the TUI.** No screen, menu, or navigation path may be written as ad hoc imperative Textual code that only exists because someone typed it directly into a `.py` file with no declarative backing. Concretely:
   - Any screen that is fundamentally "a list of labeled actions" (top-level nav, settings/config, anything with a tooltip and a target API call) **must** be expressed as menu data (dict/YAML: label, target API call, tooltip, docs reference) and rendered through the single generic `MenuScreen` renderer — not written as a bespoke screen class.
   - The **only** exception is a small, explicitly enumerated set of genuinely stateful/custom screens (run monitor, OCR corroboration diff viewer, the vendor/corporation/branch/franchiser editor, **the Groups management screen**, staff audit-review queue, the Active Services/fleet screen, the Boot Sequence loading screen, the persistent codename-header shown atop menu navigation, **the scrolling credits screen**) — **kept in sync with `v3-deepdive-14-interface-api.md` §3.2's own authoritative copy, which is the one to update first if these ever diverge again** — and even those use Textual's widget system directly (composed widgets, `.tcss` styling), never ad hoc print/input-style control flow.
   - Adding a new simple menu item must be possible by editing the menu data alone — if it requires writing a new screen class, that's a signal that item either belongs in the data-driven layer (fix the schema) or is a genuine custom-screen case (add it to the enumerated exception list explicitly, with a reason).
2. **Package-per-API, not file-per-API. No 10,000+ line files.** Every core API (OCR, Preprocessing, Inference, Workers, Save, Interface, Matching, Geo, Reconciliation, Notifications, Tool Call) is its own subpackage/directory, split internally by responsibility (e.g. `contracts.py` for types/interface, `service.py` for the thin gRPC implementation, one file per distinct concern like `engine_registry.py` / `corroboration.py`). Rationale: long files degrade Claude Code's output quality over a session (context strain → worse edits → more strain, a real downward spiral), and small stable `contracts.py` files let the model load "what this API promises" without pulling in a huge implementation file. Soft target ~300-400 lines per file; hard ceiling to be enforced via CI check (exact enforcement mode — hard fail vs. warning-with-signoff — TBD).
3. **Testing & Bench Suite — carried forward from V2's `bench.py` (the parts that were genuinely good) plus V3-architecture adaptations.**
   - Test tree mirrors the package-per-API layout: `tests/unit/` (1:1 with `core/<api>/`), `tests/integration/` (cross-API flows), `tests/e2e/` (full run through the real scheduler), `tests/interface/` (the TUI walker), `tests/bench/` (the bench suite below).
   - **Interface walker**: auto-generated (not hand-written) by iterating the same menu-data structure the app renders from, driven via Textual's `Pilot` test harness — visits every node, confirms it renders without crashing, confirms every declared tooltip/docs-reference field is actually populated. Can never go stale since it reads the live menu data.
   - **Bench suite, kept from V2**: real pipeline only, never mocked (real OCR engines, real inference, real GEO lookups against synthetic-but-genuinely-OCR-able receipts); a self-contained bench config, isolated from any real user's config; per-test process isolation so a native crash (segfault in an OCR engine/inference backend) only kills that child process and gets logged as CRASHED rather than taking the whole bench run down; empirical CPU/GPU/RAM/network classification per setting via measured wall-time-vs-CPU-time-vs-RSS deltas cross-referenced against static tags; heartbeat progress printing for long-running real-model calls; three measurement phases (fixed-overhead single-run, cumulative-stack small-set, large-set per-setting isolation).
   - **Bench suite, adapted for V3**: the bench config is just another named performance-tier profile (bench is not a bespoke one-off config); the harness dispatches runs through the real gRPC core (validates scheduler/IPC/Save API end-to-end, not just raw compute); the crash-isolation trick becomes a structural property of the architecture (OCR/Preprocessing/Inference are already separate processes) rather than a bench-only technique — the bench adds a dedicated **failure-injection mode** that deliberately crashes one engine and confirms the run scheduler survives it, directly testing the "a crash in one API must not take down the run" cross-cutting concern; a **new concurrency phase** (N simulated concurrent users running simultaneously) validates the scheduler and shared-resource limits under real multi-user load, something V2 never had since it ran strictly sequential; the hardware snapshot extends to record which machine/device each service ran on, given services may not all be co-located.
   - **CI, file-length check ("build-runner" style)**: a script walks the repo, lists every file's line count, warns past the soft cap (~300-400 lines), fails past the hard ceiling; runs on every PR alongside the unit/integration/interface-walker suite and the bench suite's regression check (compares against a stored baseline, flags regressions rather than just printing numbers).
4. **External dependencies are always swappable, never hardcoded — at every granularity, from vendor services down to individual library imports.** Any integration with an outside service (auth/SSO provider, payment processor, backup/blob storage target) *or* any external library/import (OCR engine bindings, HTTP client, image processing library, etc.) sits behind a small internal interface/adapter owned by us, with the actual implementation chosen via config or swapped by editing one adapter file — never hardcoded into call sites scattered throughout the codebase. Self-hosted installs point service-level interfaces at their own choice (their own Drive, their own S3-compatible box, their own payment account); the hosted service has a sane default. This has come up independently multiple times already (SSO, PSP, blob backup) and generalizes cleanly to imports — it's also what makes the Update API's dependency-update testing loop tractable, since a library bump's blast radius is contained to one adapter file instead of scattered call sites. Standing rule, not a case-by-case judgment call.
5. **Provider Registry pattern — any pluggable capability supports multiple simultaneous providers, not just single-selection.** OCR engines, Preprocessing presets, Inference hardware backends, Geo/Address providers, and blob backup targets (B2 + Storj in parallel) are all implemented as a registry where more than one provider can be enabled at once and run in parallel where corroboration or redundancy adds value — not a single config value swapped one-at-a-time. New pluggable capabilities default to this shape unless there's a specific reason a given capability is inherently single-choice (e.g. a payment method chosen per-transaction, an SSO provider chosen per-login — "swappable" there means "available in the registry, one selected at the moment of use," not "all run in parallel").
6. **Code repo and per-user data repos are structurally separate — never conflated.** The V3 application source (what `git pull` updates) and each user's isolated Save API data repo are different git repositories in different directories with different lifecycles. Deploying new code never touches a user's data repo, and a user's data operations never touch the code repo. This separation is what makes zero-downtime updates possible without any git-level contention between deployment and live data writes.
7. **Any new schema, taxonomy, learned-data type, or SQLite table for typed/learned data is ALWAYS Architect API's domain — no exceptions, no "just this once."** This is binding, not a convention: no other API is permitted to define its own ad hoc extensible-typed-thing, spin up its own SQLite table for learned/schema data, or invent a parallel taxonomy, even for a single narrow case. Register it through Architect's read registry (definitions) and, if it involves a learning/contribution mechanism, Architect's write submodule (temporal learning) instead. This rule exists specifically because the same "extensible typed thing" pattern was independently reinvented five separate times before Architect API was created to consolidate it — the rule is what prevents a sixth.
8. **Day-0 dependency support is a real, tracked discipline — not a one-time policy statement about Python.** This program strives for day-0 support of new dependency versions and features (Python included) for stability, performance, and output accuracy — not lagging adoption like V2, which was permanently stuck on Python 3.11 with no forward path. Concretely:
   - **Every tracked dependency is monitored continuously for release activity — stable releases AND beta/alpha/RC pre-releases**, not just reacted to after the fact once something ships stable. This monitoring is automated: a scheduled check, owned by **Dependencies Warden** (Telemetrees API's codenamed sub-API), surfaces newly detected pre-release activity and changelogs to developers rather than requiring manual changelog-watching. When something's flagged program-important, Dependencies Warden delegates the actual candidate-build-and-test execution to **Proving Grounds** (Update API's codenamed sub-API, the same general-purpose testing mechanism used for program-version channel candidates) rather than duplicating that machinery itself.
   - **Whether a given pre-release feature is "program-important" is a human judgment call**, made by the dev team when Dependencies Warden surfaces it — not something to auto-decide from a changelog diff.
   - **Once something is flagged as program-important, the goal is day-0, not day-N**: our own stable support for it (a real released `mm` version incorporating it) should ship *before* that dependency's own feature reaches *its* stable release, not sometime after.
   - This is the same Forward-Compatibility Pattern already established for Python version support (conditional installation via environment markers, feature-detection over version-checking, one compatibility shim per capability, graceful degradation) — dependency pre-release support follows the identical discipline, not a separate one-off process invented per library.
   - **Enforcement/tracking mechanism**: Dependencies Warden's findings (failed bump tests, flagged program-important pre-release features) and Health/Update's diagnosed issues all route through the **Telemetrees API** (`services/telemetrees/`), which compiles them into deduplicated, trackable GitHub Issues — turning "we monitor and try" into "and here's the automated system that ensures a tracked issue actually exists for follow-through," not just an aspiration.
9. **A PR may not exceed 99 commits — split it instead.** This exists for its own sake (a PR that large is already unreviewable, directly against the small-focused-units principle behind rule #2's file-length ceiling) and it doubles as what keeps the versioning scheme's `pp` segment safely at 2 digits rather than needing to bloat every version string for an edge case that shouldn't occur in the first place.
10. *(more rules land here as they come up — this section grows with the project, not just at the end)*

## ONNX Runtime — Feature & Setting Inventory (Inference API reference)

*(Verified via web search, not from training memory — this space moves fast. Re-verify before implementation if significant time has passed.)*

### Execution Providers — current status
- **CPU (MLAS)** — always-available fallback; actively optimized including an ARM-specific KleidiAI backend.
- **CUDA (NVIDIA)** — **CUDA 12.x is now the minimum** (11.x dropped in a recent release; pin to ORT 1.24.x if stuck on 11.x). `onnxruntime.preload_dlls()` (since 1.21) avoids DLL conflicts when PyTorch is also installed. Supports CUDA Graph capture (`enable_cuda_graph`) for repeated-shape workloads.
- **TensorRT** — two variants now: classic TensorRT EP and **TensorRT RTX EP** (consumer RTX-tuned: runtime caching, CUDA graph support, BF16, memory-mapped engines). **Engine caching (`trt_engine_cache_enable`) is required, not optional** — TensorRT builds/optimizes an engine at first run, which is slow; without caching, every session creation pays that cost again. `ORT_TENSORRT_MIN_SUBGRAPH_SIZE`/max partition iterations control how aggressively TRT claims ops vs. falling back.
- **OpenVINO** — actively developed: continuous batching for VLM pipelines by default, SnapKV-based KV-cache eviction, INT4/INT8 weight compression via NNCF, per-channel INT4 KV-cache compression, confirmed real CPU/GPU/NPU device targeting.
- **DirectML / Windows ML** — WinML dynamically loads EPs via an "ExecutionProviderCatalog," updated through Windows Update's optional preview ("D week") releases — EPs can update outside direct app control on Windows; worth Health/Update API awareness of this.
- **QNN (Qualcomm NPU)** — actively maintained; recent SDK bump added new ops and ARM64 wheel builds.
- **MIGraphX (AMD)** — the supported AMD execution provider going forward; **ROCm EP has been removed from ONNX Runtime as of the 1.23 release** (ROCm 7.0 is the last release that still includes it; 7.1+ has it removed) — MIGraphX replaces it, not an addition alongside it. Conceptually: ROCm is the platform layer (drivers/HIP/low-level libraries), the direct analog to CUDA-as-a-platform; MIGraphX is AMD's graph-optimizing compiler layer built on top of ROCm, the direct analog to TensorRT built on top of CUDA (whole-graph fusion/optimization vs. per-op dispatch). MIGraphX still requires ROCm installed underneath it — only the direct "ROCmExecutionProvider" path is retired, not the platform itself. **Real current gap**: no official Windows GPU path exists yet for MIGraphX/ROCm (confirmed via an active GitHub issue, even on AMD's own flagship "AI PC" hardware) — Windows currently falls back to CPU-only; Linux/WSL2 has the working GPU path. Treat AMD GPU acceleration as Linux-first for now, not Windows-parity with CUDA/TensorRT/OpenVINO.
- **Fallback mechanism**: `providers=[...]` is an ordered list, and fallback happens **per-node, not per-model** — a single inference session can genuinely run some ops on TensorRT, others on CUDA, others on CPU, all within one execution. This is a real, built-in graceful-degradation mechanism matching the Provider Registry philosophy — the Inference API's hardware selection should be designed around this native mechanism rather than reinventing fallback logic.
- **Node-level compatibility is not uniform across EPs** — not all ops accelerate on all EPs (independent community projects exist specifically to track this gap in Microsoft's own docs). Worth testing actual model+EP combinations rather than assuming full acceleration from an EP's presence alone.

### Session-level performance settings
- **IOBinding** — explicitly recommended for repeated inference calls; avoids unnecessary CPU↔GPU memory copies between calls.
- **CUDA Graph capture** — captures a whole kernel-launch sequence once, replays it cheaply on repeated calls with the same shape; directly relevant to the batch-first design given receipt processing's fairly repeatable input shapes.
- **Engine/session caching** — required for TensorRT (above); also worth caching the loaded session itself across receipts rather than recreating it per-call, since session creation itself is expensive.
- **Graph optimization level** (basic/extended/all) — standard ORT setting, worth setting explicitly rather than relying on defaults.
- **Memory arena settings** (`gpu_mem_limit`, `arena_extend_strategy`) — worth tuning to avoid OOM on constrained VRAM (e.g. testing on the NUC's integrated GPU or other smaller boxes).
- **`intra_op_num_threads`/`inter_op_num_threads`** — must be coordinated with the app's own asyncio/multiprocessing model (see Concurrency Model per API) or ONNX Runtime's internal threading fights the app's own threading for the same cores instead of adding a speedup.

### onnxruntime-genai (the LLM-serving layer specifically)
- **KV cache** is the central optimization for autoregressive generation: FP16 halves memory vs. FP32 with minimal quality loss; sliding-window attention caps growth for long contexts; beam search has real overhead — use greedy search unless beam search is actually needed; `past_present_share_buffer` recommended for CUDA with greedy search.
- **Model Builder tool** exports/quantizes a Hugging Face model directly to ONNX for a target precision + EP combo in one command (e.g. `-p int4 -e dml`) — activation dtype depends on the precision+EP combo chosen.
- **A real library of pre-quantized models already exists on Hugging Face** for common small models (Phi, Qwen, Llama, Gemma, Mistral, SmolLM, Granite, DeepSeek, Whisper, and more) — likely means no need to do original quantization work for whichever model gets picked.
- **INT4 weight-only quantization** is the dominant, well-supported technique for local/edge LLM deployment — current reporting describes surprisingly little accuracy impact.
- **KV-cache quantization is separate from weight quantization and riskier** — current research (2026) shows naive INT4 KV-cache quantization measurably hurts accuracy without smarter techniques (rotation-based methods like block-diagonal Hadamard rotation recover most of the lost accuracy). Not a "free" win like weight quantization — treat as opt-in/tested, not default-on.
- **Batching**: onnxruntime-genai supports a `batch_size` search option; OpenVINO GenAI's VLM pipeline uses continuous batching by default. Worth confirming the specific chosen backend's batching support directly against the model/EP combo selected, since support varies.

### Practical constraints to design around
- CUDA 12.x minimum — confirm target/self-hosted-customer hardware driver compatibility before assuming CUDA EP availability.
- TensorRT engines are hardware+model-specific and slow to build on first run — caching is mandatory, not a nice-to-have.
- CUDA and TensorRT are used together as a fallback chain (TensorRT → CUDA → CPU per-node), not CUDA replaced by TensorRT — TensorRT's ahead-of-time engine compilation is a poor fit for the variable input shapes this workload actually has (LLM prompt length, receipt image dimensions), so CUDA EP remains the real fallback rather than falling straight to CPU.
- EP support/behavior can silently shift on Windows via WinML's Windows-Update-delivered catalog — worth monitoring via Health API rather than assuming static behavior.
- Node-level EP compatibility varies per op — verify the actual chosen model against the actual chosen EP rather than assuming.

## Concurrency Model per API

Three buckets, applied consistently rather than reinvented per API:
- **Async I/O** — network calls, disk waits, waiting on another process/service. The GIL is irrelevant here; `asyncio`/`await` just avoids wasting an OS thread sitting idle. This is the dominant bucket for this system.
- **Native/GIL-released** — C/C++ libraries (OCR engines, OpenCV, rapidfuzz, ONNX Runtime) already release the GIL during their actual compute, so plain threading already achieves real parallelism for these today. No-GIL Python adds essentially nothing here.
- **No-GIL candidate** — genuine CPU-bound **pure Python** logic with no native library doing the heavy lifting (diff/merge algorithms, scoring/comparison logic, batch data transforms). Free-threading's real value is avoiding multiprocessing's IPC/serialization overhead for work currently forced into separate processes just to dodge the GIL.

| API | Model | Why |
|---|---|---|
| 1. OCR | Native (local engines) + async (Cloud Vision) | Tesseract/RapidOCR/PaddleOCR are C/C++, GIL-released, real parallelism via threading already; Cloud Vision is a network call. Corroboration/voting math is light pure-Python — negligible either way. (docTR dropped from the engine roster during its own deep-dive — see file's OCR entry and `v3-deepdive-01-ocr-api.md` §4.8 — to avoid taking on a second heavy DL framework alongside PaddleOCR's own runtime.) |
| 2. Preprocessing | Multiprocessing | OpenCV ops are native, but OpenCV's free-threaded wheels aren't ready yet (confirmed earlier) — stays on multiprocessing for genuine parallel variant generation until that changes. |
| 3. Inference | Async (caller) + native/isolated-process (generation) | Callers `await` instead of blocking a thread; actual generation runs native in its own process regardless. |
| 4. Background Workers | Per-worker classification, not one-size-fits-all | The framework needs each registered worker to declare its own nature (io/native/cpu-pure-python) and route accordingly — async event loop for I/O workers, thread pool for native-GIL-released ones, process pool for genuine CPU-bound pure-Python ones. This is itself a design requirement, not just a classification. |
| 5. Persistence (+ Reimport) | Async (SQLite I/O) + no-GIL candidate (Reimport's merge logic) | SQLite reads/writes are fast-but-blocking disk I/O, worth an async wrapper. The three-way diff/merge is genuine pure-Python CPU work — a real no-GIL candidate, though low-frequency enough it may not matter in practice. |
| 6. Interface | Async (Textual is asyncio-native) | Built on asyncio by construction. |
| 7. Matching | Native (rapidfuzz is a C/Cython extension) | Already GIL-released during the actual comparison; threading already gets real parallelism for bulk matching sweeps. |
| **8. Geo/Address** | **Async — FLAGGED, holds up the process if blocking** | Network calls to LocationIQ/Mapbox/Nominatim, per-provider rate-limited (Nominatim's 1req/sec). This one is explicitly called out: geo lookups are a known real-world stall point in the pipeline (V2's `urllib.request.urlopen()` sequential loop), so `await`-based non-blocking calls here are not optional polish. |
| 9. Reconciliation | Async orchestration; no-GIL/multiprocessing candidate for bulk propagation sweeps | Mostly triggers Persistence/Matching/Geo calls (I/O); a large "propagate this vendor correction across N old receipts" batch is a real CPU-bound-pure-Python case worth parallelizing directly. |
| 10. Notifications | Async | Sending is network-bound, full stop. |
| 11. Tool Call | Async | Dispatch itself is fast, but nearly every real tool does I/O underneath. |
| **12. Auth & Tenancy** | **Async, with one deliberate exception — FLAGGED** | SSO/session lookups are I/O. Password/token hashing (bcrypt/argon2-style) is *intentionally* CPU-expensive for security — that specifically must run off the main event loop (thread/process pool), or it blocks every other concurrent request while hashing. Concrete rule, not an afterthought. |
| 13. Logs | Async | Non-blocking rotated-file writes. |
| 14. Audit/Event Log | Async | Same as Logs. |
| 15. Ingestion | Async (Drive/upload) — scanner is client-side JS, not a Python concern | Corner-detection/stitching runs in the browser; explicitly not a backend concurrency question. |
| 16. Gateway | Async | The textbook case — FastAPI is asyncio-native by design. |
| 17. Billing & Subscription | Async | PSP webhook/API calls. |
| 18. Health | Async (status checks); negligible (diagnostic math) | Pinging other services is I/O; the wall-time/CPU-time classification math itself is cheap. |
| 19. Search/Query | Async | SQLite FTS5 queries — same reasoning as Persistence. |
| 20. Migration | No-GIL candidate for large batch runs | Migration functions are typically pure-Python row transforms — parallelizing a multi-tenant batch migration is a genuine no-GIL win; otherwise infrequent enough not to matter much. |
| 21. Update/Deployment (+ Dependency Manager) | Async (orchestration); inherits the bench workload's classification for actual dependency tests | Release-dir ops and health-check polling are I/O; dependency-bump tests run whatever OCR/Preprocessing/Inference workload they're testing. |
| 22. Review/Flagging | Async | DB reads/writes plus notification triggering. |
| 23. Setup (+ Dependency Manager) | Async (downloads); low-stakes | One-time flow, no concurrent load during setup, so this matters less than everywhere else. |
| 24. Execution Core | Async orchestration; native/isolated where it delegates to OCR/Preprocessing/Inference | Owns scheduling and sequencing, not heavy compute itself. |
| 25. Architect | Async (registry reads) + no-GIL candidate (temporal_learning's moderation-queue logic, pure-Python) | Registry lookups are fast reads; the contribution-review mechanism is modest pure-Python state transitions, not I/O-bound in the way most of this table is. |
| 26. Content Security | Native/GIL-released (local scanner subprocess, e.g. ClamAV) + async (cloud scanner API alternative) | File-signature checking is fast pure-Python; actual malware scanning is either a native subprocess call (GIL-released) or a network call (async), depending on which provider is configured. |
| 27. Telemetrees | Async | Polling upstream release feeds/issue trackers is network-bound, full stop. Its own Dependencies Warden sub-API inherits this classification. |
| 28. Account Guardian | Async | Data-export assembly and deletion-stage transitions are Persistence-mediated I/O; no compute-bound work of its own. |
| 29. Accounting Sync | Async | OAuth flows and per-receipt pushes to QuickBooks/Xero are network calls throughout. |
| 30. Status Page | Async | Its own separate process (deliberately, `v3-deepdive-51-status-page.md` §3) polling component health — I/O-bound, and intentionally isolated so it stays up when what it reports on doesn't. |
| 31. Support Ticketing | Async | DB reads/writes plus notification triggering — the same shape as Review/Flagging (#22). |
| 32. Agent Control | Async | MCP server and headless CLI are thin I/O-bound orchestration over the same gRPC calls every other client makes. **One real exception worth flagging**: its Test Orchestration sub-API's own `CrashIsolationRunner` does genuine OS-level process signalling (`v3-deepdive-56-test-orchestration.md` §3.2) — not compute-bound, but not a plain network call either, and the only component in this system that deliberately signals another service's worker process. |

## Branding & Naming

- **Keymaster — self-hosted licensing, a completely separate closed system, NOT part of this repo.** Real design flaw caught and fixed mid-session: an earlier version of this plan put license-validation logic inside Billing API, which ships inside every self-hosted release clone — meaning the "authority" checking a license would sit on the customer's own disk, fully readable and patchable by the exact person it's meant to validate. Not a real check. The fix: licensing lives entirely outside the `receipt-system-v3` codebase, in its own separate repo DOMTRI alone deploys, whose source never reaches a customer's machine.
  - **What Billing keeps**: hosted multi-tenant subscription management only (logged-in webapp users, session-based). Has nothing to do with self-hosted licensing.
  - **What a self-hosted license actually is**: a genuinely separate entity from a hosted subscription — a business buys a license via checkout (same PayMongo/Xendit rails, different SKU/product than hosted), Keymaster generates a random high-entropy key (`RESIBO-XXXX-XXXX-XXXX-XXXX`) tied to purchaser contact info and payment status, delivered by transactional email — no SSO/account required for the purchase itself, avoiding unnecessary friction for a B2B buyer. Modeled as a subscription (must keep paying to keep getting *updates*) even though the software itself keeps running indefinitely once cloned — the license only ever gates whether new releases keep flowing.
  - **Where the key is used**: entered once during Setup API's first-run wizard, stored in the top-level config (same outside-every-release-clone location as every other secret).
  - **The actual gate**: the code repo must be private, not public — a plain `git clone` against a public repo has nothing to intercept, so privacy is the precondition that makes gating possible at all. Update API calls Keymaster (a plain outbound HTTPS call, same category as calling PayMongo/GitHub/LocationIQ) before each clone attempt; Keymaster validates the key and, if current, mints a short-lived scoped GitHub token for that one clone. A lapsed license simply stops producing valid tokens — the next clone fails at GitHub's own auth step, no custom enforcement needed. **Fail-open, always**: a Keymaster outage or check error never blocks the already-running instance, only blocks *fetching something new* — never risks locking a business out of its own tax/financial data over a licensing hiccup.
  - **Preventing key sharing/reuse beyond what was paid for**: activation is bound to a specific installation, not just "is this key valid" — Setup API generates a random instance ID on first run (deliberately not a hardware fingerprint, since hardware changes are legitimate and a fingerprint-based lockout risks exactly the false-positive customer lockout already ruled unacceptable). Keymaster tracks which instance ID(s) a key is currently activated on, enforces the purchased instance count, allows a legitimate transfer (deactivate old, activate new) for real hardware migrations, and flags rapid instance-switching as the pattern actual sharing would look like.
  - **Preventing brute-forcing and datamining the license list**: high-entropy keys make guessing computationally infeasible on their own; the validation endpoint is rate-limited (same principle as Gateway's own rate-limiting); no endpoint ever enumerates or lists licenses; every failure mode (wrong key, unactivated, expired) returns an identical generic rejection, since a validator that reveals *why* a key failed leaks information an attacker could use to narrow down real keys; standard data-security practice for what's genuinely sensitive (encryption at rest, access restricted to Keymaster's own process, backups, anomaly-monitoring on validation query volume).
  - **Enforcement philosophy, stated plainly**: technical measures here are a deterrence/detection layer, not an unbreakable barrier — that's a structural fact about any self-hosted server software the customer has root access to, not a flaw to keep chasing. The real enforcement backbone for B2B sales is the license agreement itself plus audit rights, standard industry practice for exactly this class of product; Keymaster's job is raising the bar for casual/accidental violation and keeping legitimate customers current on security patches, not achieving unbreakable copy protection.

- **Company/product context**: ReNoVaiT (Francis's hardware-restoration brand — "renovation" of old PC parts) and DOMTRI Foundation jointly own this project; domain is `renovait.qzz.io`, matching the pattern of Francis's other subdomain projects (NGRF, NewGen, thedirectorslist).
- **Product subdomain**: `resibo.renovait.qzz.io` — "resibo" is Tagalog for "receipt," chosen to match the project's own identity (per the existing pattern of naming subdomains after the project, not the parent brand) rather than tying it to ReNoVaiT's hardware theme, which doesn't fit a tax/receipt tool. Alternates considered: `kuwenta` (Tagalog "account/bill"), `tala` (Tagalog "record," also "star").
- **Single-origin correction**: `api.resibo.renovait.qzz.io` was originally planned as a separate subdomain, but since Gateway now serves both the webapp and the API from one process, a genuine cross-origin split no longer buys anything — it just re-introduces CORS configuration and cross-origin cookie complexity for no benefit. **`resibo.renovait.qzz.io` is the single origin for both**, with the webapp calling API routes as relative same-origin paths. `api.resibo.renovait.qzz.io` is kept **reserved, not required** — a real future use exists (a genuine third-party/programmatic API surface, or the Pages-hybrid optimization noted below), so the name isn't wasted, but nothing in v1 depends on it existing.
- **Webapp hosting is unified across both tenancy modes — Gateway serves the static build directly through the Tunnel in both self-hosted and hosted multi-tenant mode** (a Cloudflare Pages split for hosted mode was considered and reverted: Pages' single/branch-deployment model doesn't cleanly support serving different frontend versions to different users based on an individually-chosen channel, and having frontend-version-routing and backend-version-routing as two separate mechanisms risked them disagreeing — see Gateway API entry for the full reasoning). CDN-like performance recovered via Cloudflare Cache Rules on the Tunnel-routed static-asset paths instead of a separate hosting product; a Pages-for-Stable-only hybrid is a legitimate later optimization, not a v1 decision (and would be the actual trigger for bringing the reserved `api.` subdomain into real use).

## Versioning Scheme

**Program version**: `x<MM>.<mm>.<pp> [code-repo commit hash]`
- `MM` = product generation (V1=01, V2=02, V3=03), each with a codename. First real V3 release correctly lands on `x03.00.00`, not restarting at 1.
- `mm` = increments per merged PR.
- `pp` = increments per commit within the current PR (doubles as a human-readable commit label). **Kept at 2 digits, not 3** — a PR exceeding 99 commits is already a reviewability smell independent of version numbering, so the fix is a hygiene rule (any PR over 99 commits must be split — see Repo Hygiene) rather than bloating every version string to accommodate something that shouldn't happen. Same reasoning applies identically to the API version's `pp` below.
- Pre-release work (before the first real release) starts at `x00.01.00` and climbs until ready to become `x03.00.00`.
- The bracketed commit hash pins the exact build, since `mm.pp` are sequential counters, not content-addressable.

**Major version codenames (Z→A)**: minerals/gemstones — chosen over TrueNAS's aquatic theme to fit V3's own narrative (something formed under pressure into what's meant to last). A couple of letters (Q, X) have thin natural coverage and may need a compound/creative name when reached. Living list, extended as real major versions actually ship, not front-loaded:
- `x03.00.00` → **Zircon** (one of the oldest minerals on Earth — fitting for the first real release after V1/V2)
- `x04.00.00` → **Yttrium** *(or "Yellow Sapphire" if staying strictly gemstone — open)*
- `x05.00.00` → **Xenotime** (a real, if obscure, rare-earth mineral — solves the X gap)
- `x06.00.00` → **Wulfenite**

**Version control strategy for the four channels — tags for three, a real branch for one, not four uniform branches.** Stable, Beta, and Alpha are **tags**, not branches: they're just labels pointing at specific commits along one single linear history, promoted forward over time — a branch would imply divergent development needing constant merge/rebase to stay in sync with mainline, which is overhead these three don't actually need since nothing about them ever diverges. **LTSC is the genuine exception and gets a real branch**: actual long-term-support channels need backported fixes (a security patch cherry-picked onto the LTS line without dragging in newer feature work) — that requires a real fork point and its own subsequent patch commits, which tags can't represent. **ASCII art scope, sharpened accordingly**: tag-based channels need zero extra work (they're points on the one tree that already retains every codename's art). The LTSC branch only ever needs its own codename's art plus everything up to its fork point — it will never run as a later version, so it has no need for future codenames it hasn't reached, and gets everything up to its fork point automatically by being a fork of a tree that never deletes old codename files.

**API version**: `a<MM>.<mm>.<pp>`, same shape, per-API.
- `MM` reflects lineage: brand-new-to-V3 APIs (Health, Search, Migration, Update, Review/Flagging, Auth, Logs, Audit, Ingestion, Gateway, Billing, Architect) launch at `a01.00.00`; APIs with real ancestry to V1/V2 (OCR, Preprocessing, Inference, Workers, Persistence, Interface, Matching, Geo, Reconciliation, Notifications, Tool Call) launch already at `a02` or `a03` depending on lineage depth.
- **Confirmed**: `MM` also increments for any subsequent breaking change to that specific API within V3's own lifetime — lineage sets the starting point, but breaking-change semantics continue normally from there. Same principle as the whole-program's `MM` not being frozen at 3 forever.

**Per-receipt version stamps** (via Persistence's Historian sub-package):
- `first_scan`: program version + relevant API versions + code-repo commit + Historian event reference + timestamp — **immutable once set**.
- `latest_reconciliation`: same fields — **updates on every reprocessing/reconciliation event**.
- **Full edit history**: every Historian event referencing a given receipt, each stamped with actor (worker/LLM/human), program+API version, and the code-repo commit — this is what makes "show this receipt's edit history" a simple filtered query rather than a bespoke feature.

## Python Version Support

**Policy**: day-0 support for new Python releases, not a lagging adopter like V2 (stuck on 3.11). The test/bench suite's CI matrix includes **3.15 (currently beta) and 3.16 (currently alpha) pre-release interpreters now**, verified continuously rather than discovered at their stable release. Dependency availability remains the real gate (third-party C-extension wheels catching up, e.g. OpenCV's free-threading status) — but our own code has zero excuse to lag, since none of it should need version-gated rewrites when a release goes stable.

**The Forward-Compatibility Pattern** — the same shape of decision recurred three times (frozendict, Tachyon/py-spy, zipfile) independently, so it's named once here as a reusable principle rather than re-derived per feature:

1. **Conditional dependency installation via environment markers** — a dependency manifest entry like `frozendict; python_version < '3.15'` or `py-spy; python_version < '3.15'`, resolved automatically by `uv` at install time. The older dependency isn't just unused on newer Python — it's never installed at all.
2. **Feature-detection over version-checking, wherever the target API's shape might still be in flux.** Gate on `hasattr(zipfile.ZipFile, 'remove')`, not `sys.version_info >= (3, 16)`. A still-alpha API (like 3.16's `zipfile.remove()`/`repack()`) can shift shape before stable release — a hard version check would need updating if that happens; a feature-detection check just naturally stops matching and falls through to the safe default, surviving the change without a code update.
3. **One centralized compatibility shim per capability**, not scattered version-conditional logic across call sites — a single small module resolves "which implementation is active" once, at import time; the rest of the codebase never needs to know or care which one it's using. When the minimum-supported Python version eventually gets raised past the cutover point, only that one shim simplifies — every other call site never changes.
4. **Graceful degradation to the existing safe behavior when a newer capability isn't available** — not a special case, just another instance of the general "everything degrades gracefully" philosophy already baked into this plan.

**Applied concretely:**
- **`frozendict`** (immutability pillar): the PyPI `frozendict` package installed only via a `python_version < '3.15'` marker; one compat shim resolves to the 3.15+ builtin; zero call-site changes ever, including when the min-version floor eventually gets raised past 3.15 (only the shim gets simplified/deleted then).
- **Health API's diagnostic layer (Tachyon/py-spy)**: `py-spy` installed only via `python_version < '3.15'`; the existing Provider Registry's diagnostic-provider selection naturally resolves to Tachyon (3.15's built-in `profiling.sampling`) on newer installs since py-spy isn't even present to be considered, and to py-spy on older ones — zero additional branching logic needed beyond the Provider Registry mechanism that already exists.
- **Content Security's archive remediation (`zipfile.remove()`/`repack()`, 3.16)**: implemented now, gated by `hasattr()` feature-detection. Strictly additive — where available, a clean zip containing one bomb-prone member gets that member stripped and the rest extracted; where not available, the existing safe default applies (reject the whole archive). Safe to build against a still-alpha API today specifically because the fallback path is already correct, not a placeholder.
- **`lazy import`** (PEP 810, 3.15+): usable immediately via the sanctioned `__lazy_modules__` compatibility mechanism — a module list that makes listed imports lazy on 3.15+ and is simply inert (imports stay eager, today's normal behavior) on older Python. No version branching needed at all, works correctly on every supported version simultaneously.
- **`abi3t` (stable ABI for free-threaded builds)**: not ours to build — a packaging concern for upstream C-extension maintainers (OpenCV, NumPy, etc.), not application code. Continue tracking OpenCV's free-threading readiness as already planned; this just changes what unblocks it.
