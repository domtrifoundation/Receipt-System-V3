# Pre-Stable/LTSC Bench Validation Checklist

Every item in this document is a reasoned default that shipped without real measurement behind it — stated explicitly as provisional throughout the planning corpus, never hidden as more final than it was. This is the actual to-do list for closing that gap, **required before the x03.00.00 Stable/LTSC release**, not before any earlier Alpha/Beta tag.

---

## THE ONE RULE THAT MATTERS MOST — READ THIS FIRST

**Claude Code: do not generate, synthesize, or fabricate fake receipt images for any of the validation work in this document. Ask the user for real, physical receipt scans instead — actual photographs or scans of actual paper receipts, the messier and more realistic the better.**

This is not a preference, it's a correctness requirement. Every OCR/Preprocessing/Inference/Matching bench item below exists specifically to validate this system's behavior against the real-world mess this project's own documents describe repeatedly — uneven lighting, non-white backgrounds, skewed angles, faded thermal print, handwriting, folded/creased paper. A synthetically generated "receipt" (whether rendered from a template, generated by an image model, or assembled programmatically) cannot reproduce this mess in a way that's actually representative — it will systematically be cleaner, more uniform, and more forgiving than real input, which means every bench result measured against synthetic data would be optimistic in exactly the way that matters least to catch. A bench pass that "validates" against fake receipts isn't validation at all; it's a number that looks like validation.

**If real receipt scans aren't available yet, the correct action is to ask the user for them and wait — not to proceed with synthetic substitutes and mark the item done.** A dozen or two dozen real, varied receipts (different vendors, different lighting conditions, different physical states) is worth more than thousands of synthetic ones for every item in Part 1 below.

---

## A REAL PRIVACY REQUIREMENT — READ THIS SECOND, BEFORE COLLECTING ANY RECEIPTS

**A real receipt scan contains real, sensitive personal information — a TIN, a real purchase history, sometimes a real name.** "Use real receipts" and "commit real receipts to a git repository forever" are two very different things, and this document's own emphasis on real scans should never be read as license to do the second without thinking about it.

- **Never commit real receipt images to the repository directly.** A test-fixtures directory containing real financial data (`tests/fixtures/real_receipts/` or wherever this ends up living) must be added to `.gitignore` — real receipts stay on the local machine of whoever is running this validation, never in git history, which is effectively permanent and effectively public the moment this repo is public.
- **Whose receipts these are matters.** The straightforward, low-friction answer: the developer's own receipts, with the developer's own consent, since it's their own data and their own decision to use it for this purpose. Do not use receipts belonging to someone else without their own explicit, informed consent — this isn't a hypothetical concern given `docs/LEGAL_REVIEW_NEEDED.md`'s own findings about exactly this kind of data.
- **CI/automated pipelines never get real receipts at all.** Real, sensitive fixtures are strictly a local, manual-validation-only concern — Part 1's own bench validation is explicitly a human-initiated task before a Stable/LTSC tag, never something GitHub Actions or any other automated CI runs against real personal data. A separate, small set of either fully synthetic or genuinely-consented-and-anonymized sample images can live in CI for structural testing ("does the pipeline run without crashing"), which is a different, lower-stakes question than the accuracy validation this document is actually about — keep the two purposes and the two fixture sets genuinely separate, never conflated.
- **`v3-deepdive-56-test-orchestration.md` §6** adds a real, structural heuristic check flagging a fixture directory that looks synthetic — a second, non-trust-dependent safeguard behind the instruction above, not a replacement for actually following it.

## Part 1 — Requires real receipt scans specifically

- [ ] **OCR: RapidOCR vs. PaddleOCR corroboration value** (`v3-deepdive-01-ocr-api.md` §4.4) — do the two engines actually diverge enough on real receipts to be useful run together, or is one alone sufficient? Answered by measurement, not assumption.
- [ ] **OCR: Tesseract PSM bench sweep** (`v3-deepdive-01-ocr-api.md` §4.2/§9) — confirm `psm=6` (the current reasoned default) against the real candidate set `{3, 4, 6, 11}`.
- [ ] **Inference: constrained-decoding schema-compliance** (`v3-deepdive-02-inference-api.md` §11) — does the chosen preset/hardware combination actually produce 100% schema-valid output on real receipts, not just per the library's general claim?
- [ ] **Inference: reasoning-model degenerate-output check** (`v3-deepdive-02-inference-api.md` §11) — confirm the reasoning-tuned presets never reproduce V2's canned-stub failure mode, using real receipts that would actually trigger reasoning-preset usage.
- [ ] **Inference: vision preset comparison** (`v3-deepdive-02-inference-api.md` §12) — Phi-4-multimodal (current default) vs. the two named alternatives, real accuracy/speed comparison on real receipt images.
- [ ] **Preprocessing: fixed variant set win-rate** (`v3-deepdive-03-preprocessing-api.md` §7/§12) — which of the current default-enabled variant kinds actually earn their keep against real receipts.
- [ ] **Preprocessing: CLAHE clip limit / tile grid size** (`v3-deepdive-03-preprocessing-api.md` §4.3/§7) — validate the current literature-typical starting values against this project's own real receipt population.
- [ ] **Preprocessing: deskew method** (`v3-deepdive-03-preprocessing-api.md` §4.5) — confirm contour (current default) over Hough against real skew angles a phone-captured receipt actually produces.
- [ ] **Matching: reverse-scan plausibility-window heuristic** (`v3-deepdive-15-matching-api.md` §4/§8) — validate the current placeholder scoping against real receipt layouts.
- [ ] **Format Normalization: HEIC round-trip fidelity** (`v3-deepdive-42-format-normalization.md` §8) — **specifically needs real iPhone photos**, not any receipt image — whether HEIC-to-archival-codec conversion loses any measurable quality at the configured setting.
- [ ] **temporal_learning: category granularity calibration** (`v3-deepdive-40-temporal-learning.md` §12) — how fine-grained vendor categories need to be before category-default learning becomes genuinely useful, calibrated against real vendor/category data as it accumulates from real receipts.

## Part 2 — Requires real operational data, not receipt scans (don't conflate the two)

These need real usage patterns, real load, or real elapsed time — not receipt images. Worth keeping genuinely separate from Part 1 so this document doesn't get treated as "just feed it more receipts and everything gets measured."

- [ ] **Auth: session store lookup bench** (`v3-deepdive-05-auth-tenancy-api.md` §11) — confirm `ValidateSession` stays a single indexed SQLite read under realistic concurrent load, not receipt-dependent.
- [ ] **Execution Core: debounce/max-wait defaults** (`v3-deepdive-10-execution-core-api.md` §12/§14) — needs real traffic patterns (how often do batches of receipts actually arrive close together in real usage).
- [ ] **Setup: recommended-settings scoring coefficients** (`v3-deepdive-11-setup-api.md` §5.4) — this is the natural *consumer* of the bench results from Part 1 above (OCR/Preprocessing/Inference) — do this one last, after those are done, not in parallel.
- [ ] **Background Workers: exact job cadences** (`v3-deepdive-12-background-workers-api.md` §6.4/§9) — real operational data on how often session cleanup, blob backup verification, etc. actually need to run.
- [ ] **Health: reservation TTL default** (`v3-deepdive-20-health-api.md` §11) — real session-lifetime data across OCR/Inference/Preprocessing's own actual usage patterns.
- [ ] **Historian: query performance at scale** (`v3-deepdive-29-historian.md` §14) — needs realistic *volume* (many receipts, many history entries per user over time), which can reasonably use synthetic bulk data for volume/load purposes specifically — this is a genuine exception to the "always use real scans" rule, since the concern here is query performance under data volume, not recognition accuracy against real-world image mess. Synthetic records with realistic *shape* (not receipt images) are fine for this one item only.
- [ ] **Disaster Recovery: restore time/bandwidth estimates** (`v3-deepdive-33-disaster-recovery.md` §9) — needs real backup data volume to exist first; can't be measured before there's a real instance with real accumulated data.
- [ ] **Webhook Manager: renewal lead-time default** (`v3-deepdive-35-webhook-subscription-manager.md` §10) — needs real observed Google Drive channel-expiry behavior over real elapsed time, not receipt-related at all.

## How to actually run this before a Stable/LTSC tag

1. Confirm every Part 1 item has real receipt scans available. If not, **stop and ask the user for them** — do not proceed with synthetic substitutes for these specific items.
2. Run each bench case as already specified in that item's own owning document's "Testing hooks" section — the mechanism is already designed in every case, this document doesn't re-specify *how*, only *what's outstanding* and enforces the real-data requirement.
3. Where a bench result confirms the current default, mark it validated (update that document's own open-questions section from "reasoned, provisional" to "confirmed, measured" — this document's own job is done once the real deep-dive documents reflect real results, not to become a second source of truth that could drift from them).
4. Where a bench result contradicts the current default, update the default *and* log the change in `v3-plan-03-decisions.md`, the same discipline every other real correction in this corpus already followed.
5. Do not tag x03.00.00 Stable/LTSC until every Part 1 item is checked off with real data behind it. Part 2 items are worth doing but are lower-stakes and less likely to surface a correctness problem — reasonable to tag Stable with a couple of Part 2 items still pending real-world tuning, less reasonable for Part 1.
